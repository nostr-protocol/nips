NIP-62
======

Request to Vanish
-----------------

`draft` `optional` `relay`

This NIP offers a Nostr-native way to request removal of a key's events from relays, subject to the deletion-protection exception below for implementations supporting [NIP-XX](XX.md). When applying an effective purge, relays remove the event data from their databases. These protocol rules do not determine independently applicable obligations of relay operators.

## Request to Vanish from Relay

Kind `62` requests a specific relay to delete everything, including [NIP-09](09.md) Deletion Events, from the `.pubkey` until its `.created_at`, except marked events on implementations supporting [NIP-XX](XX.md).

```yaml
{
  "kind": 62,
  "pubkey": <32-byte hex-encoded public key of the event creator>,
  "tags": [
    ["relay", "<relay url>"]
  ],
  "content": "<reason or note>",
  //...other fields
}
```

The tag list MUST include at least one `relay` value. 

Content MAY include a reason or a legal notice to the relay operator. 

Relays MUST fully delete any events from the `.pubkey` if their service URL is tagged in the event, except marked events on implementations supporting [NIP-XX](XX.md).

Relays SHOULD delete all [NIP-59](59.md) Gift Wraps that p-tagged the `.pubkey` if their service URL is tagged in the event, deleting all DMs to the pubkey. NIP-XX does not exempt marked gift wraps from this recipient-based purge.

Relays MUST ensure the deleted events cannot be re-broadcasted into the relay. For relays supporting NIP-XX, this requirement MUST NOT reject or suppress marked events under the request's author-based purge authority, including marked events first received after the request. Recipient-based purge behavior remains unchanged.

Relays MAY store the signed request to vanish for bookkeeping.

Paid relays or relays that restrict who can post MUST also follow the request to vanish regardless of the user's status, subject to the same NIP-XX exception when supported.

Publishing a deletion request event (Kind `5`) against a request to vanish has no effect. Clients and relays are not obliged to support "unrequest vanish" functionality.

Clients SHOULD send this event to the target relays only. 

## Global Request to Vanish

To request ALL relays to delete everything, the event MUST include a `relay` tag with the value `ALL_RELAYS` in uppercase. 

```yaml
{
  "kind": 62,
  "pubkey": <32-byte hex-encoded public key of the event creator>,
  "tags": [
    ["relay", "ALL_RELAYS"]
  ],
  "content": "<reason>",
  //...other fields
}
```

Clients SHOULD broadcast this event to as many relays as possible.

## Deletion Request Protection

Relays and clients supporting [NIP-XX](XX.md) MUST exempt marked target events from the request's author-based purge and corresponding republication ban. This applies to relay-specific and `ALL_RELAYS` requests. All non-exempt targets follow their ordinary rules.

Requests, deletion records, author cutoffs, and automatic author deactivation MUST NOT cause an otherwise acceptable marked event to be deleted, suppressed, or rejected under that author-based authority. This includes marked events whose `created_at` falls within the request's author-purge range, regardless of whether the event was received before or after the request.

The exception does not apply to recipient-based gift-wrap purges under this NIP and [NIP-59](59.md). A sender's marker cannot waive the recipient's independently defined deletion authority. NIP-XX adds no recipient cutoff or timestamp condition.

Implementations MUST establish an incoming event's validity and protection status before applying an author-based deletion record that would reject or suppress it. A marker on the request itself does not protect its targets. The complete tag, kind, expiration, republication, and support requirements are defined in NIP-XX.

Marked events remain subject to independently applicable storage policy and their original signed NIP-40 expiration, if any. Expiration does not revoke the marker's author-based deletion exception for copies that remain stored. This exception does not require permanent storage or alter the processing of unmarked targets.
