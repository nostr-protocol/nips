NIP-9B
======

Verifiable Community Rules
--------------------------

`draft` `optional`

This NIP defines an addressable event that lets a community authority publish
a **machine-readable, signed rules document**. Clients can fetch this event
before submitting a post and check the draft locally, surfacing violations
before send. Relays and feed filters can apply the same rules.

[NIP-29](29.md) leaves the capabilities of group roles to relay-side policy.
This NIP exposes a portable, declarative subset of that policy. It also
supports legacy [NIP-72](72.md) communities, where it complements post-hoc
`kind:4550` approvals. NIP-72 is now unrecommended, so new implementations
SHOULD target NIP-29.

The rules are carried by `kind:34551`. This NIP does not add a `rules` tag to
NIP-72's `kind:34550` community definition.

## Event definition

The rules document is an addressable event of `kind:34551`. Its `content` is
not interpreted by this NIP and SHOULD be empty.

This example binds rules to a NIP-29 group:

```yaml
{
  "kind": 34551,
  "pubkey": "<relay-self-pubkey>",
  "created_at": <Unix timestamp in seconds>,
  "tags": [
    ["d", "<group-id>"],
    ["a", "39000:<relay-self-pubkey>:<group-id>", "wss://groups.example.com"],

    // One allowed event kind, with optional size and daily quota.
    // Form: ["k", "<kind>", "<max-bytes?>", "<max-per-author-per-day?>"]
    ["k", "1111", "16384", "50"],
    ["k", "20", "262144", "10"],
    ["k", "30023", "262144", "5"],

    // Per-pubkey policy. May appear multiple times.
    // Form: ["p", "<hex>", "<allow|deny>", "<role?>"]
    ["p", "<trusted-pubkey>", "allow", "contributor"],
    ["p", "<bad-actor-pubkey>", "deny"],

    // Web-of-trust gates. Any one passing gate is sufficient.
    ["wot", "<root-pubkey>", "2"],

    ["max_event_size", "524288"],
    ["min_rules_created_at", "1746604800"]
  ],
  "content": ""
}
```

### Tag semantics

- **`d`**: REQUIRED exactly once, with a non-empty value. For NIP-29 it MUST
  equal the group ID. For NIP-72 it SHOULD match the community definition's
  `d` value.
- **`a`**: REQUIRED exactly once. It binds the rules document to one
  community, using the coordinate and relay forms defined in "Bindings".
  Other addressable event kinds MUST NOT be used as community bindings.
- **`k`**: REQUIRED one or more times. Each occurrence allows one event kind.
  The first value is a canonical base-10 kind integer between 0 and 65535.
  The optional second value is a non-negative base-10 byte limit. The optional third value is a
  non-negative base-10 daily quota. An empty optional value means no limit
  for that field. A kind MUST occur at most once. Events whose kind has no
  `k` entry MUST be rejected.
- **`p`**: OPTIONAL, zero or more times. The first value is a lowercase
  32-byte hex pubkey, the second is `allow` or `deny`, and the optional third
  is a free-form role label with no normative meaning. Any matching `deny`
  overrides every other rule. A matching `allow` bypasses only the `wot`
  gates. It does not bypass `deny`, the kind allowlist, size limits, or
  quotas.
- **`wot`**: OPTIONAL, zero or more times. The first value is a lowercase
  32-byte hex root pubkey and the second is a positive base-10 maximum
  follow-graph depth. The root is at depth zero, a direct follow is at depth
  one, and so on. Multiple gates are ORed. The lookup mechanism is not
  fixed. Clients MAY use NIP-02 follow lists, NIP-85 trusted assertions, or
  another locally available source, but identical verdicts require identical
  graph inputs.
- **`max_event_size`**: OPTIONAL, zero or one time. Its non-negative base-10
  value is a hard byte cap applied in addition to the `k` tag's size limit.
- **`min_rules_created_at`**: OPTIONAL, zero or one time. Its non-negative
  base-10 value is an anti-rollback floor. It MUST NOT exceed the rules
  event's `created_at`. An absent value is equivalent to zero.

Unknown tags MUST be ignored. Recognized tags MUST have exactly the number
of elements shown above, counting optional elements only when present.
Additional elements make the recognized tag malformed. A document with a
malformed recognized tag, a duplicate singleton tag, a duplicate `k` kind, or
an invalid coordinate is invalid as a whole. Implementations MUST NOT
partially enforce an invalid document.

## Bindings and authority

### NIP-29

Use the address of the group's `kind:39000` metadata event, including the
relay URL as the `a` tag's third element:

```yaml
["a", "39000:<relay-self-pubkey>:<group-id>", "<group-relay-url>"]
```

This is the same identity represented by the group `naddr` described in
NIP-29. The relay URL is REQUIRED and is part of the binding. It MUST be a
`ws://` or `wss://` URL for the relay used to locate the group metadata.

The rules event's `pubkey` MUST equal both the coordinate author and the
pubkey that signs the group's current `kind:39000` event. NIP-29 defines
this as the relay `self` key. Clients SHOULD also compare it with the
relay's NIP-11 `self` field when that field is available.

A NIP-29 rules event is group metadata, not a user post. It does not use an
`h` tag as its community binding. User events submitted to the group still
use `["h", "<group-id>"]` exactly as specified by NIP-29.

Group IDs are not globally unique. The same ID on different relays identifies
different relay-scoped group instances, even when those instances share
history. After a migration or fork, clients MUST resolve rules from the
currently selected group relay and MUST NOT apply another relay's rules to
that instance. The new relay MUST publish rules under the authority of its
own current `kind:39000` metadata. Copying an old rules event does not make
it authoritative for a different relay binding.

### Legacy NIP-72

Use the address of the `kind:34550` community definition:

```yaml
["a", "34550:<community-owner-pubkey>:<community-d-identifier>", "<optional-relay-url>"]
```

The rules event's `pubkey` MUST equal the coordinate author and the pubkey
of the community definition. Clients SHOULD fetch rules from the community's
preferred `requests` or `approvals` relays when available.

## Selecting the active rules document

Clients MUST apply these steps instead of accepting an arbitrary event
returned by a relay:

1. Resolve the expected community coordinate and authority as above.
2. Fetch `kind:34551` candidates with the expected author, `d` value, and
   `a` coordinate from the community relay or another source authorized by
   the applicable community NIP.
3. Verify each event's signature, binding, authority, and complete tag
   validity. Discard invalid candidates.
4. Apply the rollback floor described below.
5. Select the remaining candidate with the highest `created_at`. Break ties
   by retaining the lowest event ID, as in NIP-01.

If no authoritative candidates are returned, no rules are in force. Absence
of rules MUST NOT be treated as deny-by-default. If candidates exist but all
are invalid or are removed by the rollback floor, selection is indeterminate,
not absence of rules. Clients SHOULD query another authorized source. The
indeterminate composer and relay behavior below applies.

### Rollback floor

Clients MUST persist the highest observed `min_rules_created_at` separately
for each community binding. For NIP-29, the binding key includes both the
`kind:39000` coordinate and its relay URL.

When evaluating a candidate set, a client MUST:

1. Start with its persisted floor.
2. Raise the floor to the highest `min_rules_created_at` among otherwise
   valid candidates, and persist the new value.
3. Discard every candidate whose `created_at` or
   `min_rules_created_at` is below that floor.

Consequently, once an owner ratchets the floor, every later rules document
MUST carry a floor at least as high. Owners SHOULD set
`min_rules_created_at` equal to the new document's `created_at` whenever
they intentionally tighten the rules.

This mechanism only protects clients after they observe a ratcheted
document. It cannot reveal a newer document withheld from a fresh client,
and it cannot stop a compromised owner key from publishing new permissive
rules.

## Validating a candidate event

Determine each candidate's community binding using the applicable community
NIP. For NIP-29, use the candidate's `h` group ID together with the selected
group relay. For NIP-72, use the community tags defined by NIP-72 and NIP-22,
including the uppercase `A` community tag on replies and the legacy `a` form
where allowed. A cross-posted candidate is evaluated separately for each
community.

Validation has three possible outcomes: **accept**, **violation**, or
**indeterminate**. Given the same candidate, community binding, event history,
follow graph, and persisted rollback state, implementations MUST reach the
same outcome. NIP-9B does not pretend that independent relays possess
identical history or follow graphs.

Evaluate these checks in order and stop at the first violation or
indeterminate outcome:

1. **Author deny**: return a violation if any `p` tag denies the author.
2. **Kind allowlist**: return a violation if no `k` tag allows the kind.
3. **Per-kind size**: return a violation if the event exceeds the `k` size
   limit.
4. **Global size**: return a violation if the event exceeds
   `max_event_size`.
5. **Daily quota**: apply the corresponding `k` quota as defined below.
6. **Web of trust**: unless the author has a matching `allow`, evaluate every
   `wot` gate. One passing gate satisfies this step. If all evaluated gates
   fail and at least one other gate is indeterminate, return indeterminate.
   If every gate is evaluated and none passes, return a violation.

An explicit `allow` affects only step 6.

### Event size

Both size limits use the byte length of the UTF-8 encoded NIP-01 event-id
serialization:

```yaml
[0, <pubkey>, <created_at>, <kind>, <tags>, <content>]
```

Use the exact JSON serialization rules from NIP-01, with no insignificant
whitespace. The `id` and `sig` fields are not included. This definition lets
a composer calculate the size before signing and avoids dependence on JSON
object key order.

### Daily quotas

For quota `q`, calculate the candidate's UTC day as
`floor(created_at / 86400)`. The interval is
`[day * 86400, (day + 1) * 86400)`, using Unix seconds. Local time zones and
relay receipt times MUST NOT be substituted for `created_at`.

Count distinct event IDs, excluding the candidate, with all of these
properties in the verifier's available history:

- the same author and kind as the candidate;
- the same community binding, including relay scope for NIP-29;
- a `created_at` in the same UTC day.

Every version of a replaceable or addressable event counts separately.
Deletion requests do not subtract from the count. The candidate violates the
rule when the count is greater than or equal to `q`. In particular, `q = 0`
rejects every candidate of that kind.

If the verifier lacks sufficient history to determine the count, the result
is indeterminate, not a successful quota check. Relays enforcing quotas
SHOULD apply their normal timestamp and NIP-29 late-publication policies so
authors cannot evade a current-day quota with backdated or future-dated
events. Those acceptance policies are outside this NIP.

A verifier that cannot finish a WoT lookup because of missing data or a
resource cap also returns indeterminate. It MUST NOT convert an unexamined
gate into a pass.

## Client behavior

### Composer

Before publishing an event into a community, clients SHOULD fetch and select
the active rules document, then validate the draft. They SHOULD surface the
specific violation before send, such as `kind_not_allowed`,
`kind_size_exceeded`, `quota_exceeded`, or `wot_gate_failed`.

A client MAY send when no rules document exists. If validation is
indeterminate, the client MUST NOT present the draft as compliant. It MAY
send only after explicit user confirmation that identifies the unchecked
rule.

Each new version of a replaceable or addressable post is a new candidate and
counts separately toward the daily quota.

### Reader

Clients displaying a community feed MAY filter events with the active rules
as a local presentation policy. For legacy NIP-72 communities, this can
complement `kind:4550` approval filtering.

Reader filtering does not retroactively change whether a relay accepted an
event. Readers SHOULD NOT hide an event solely because its quota or WoT
status is indeterminate.

## Relay behavior

Relays MAY enforce the selected rules by rejecting non-conforming `EVENT`
submissions with a NIP-01 `OK` response whose message uses the `blocked:`
prefix and identifies the violated rule.

A relay that advertises NIP-9B enforcement MUST NOT accept a candidate as
rule-compliant when a required quota or WoT check is indeterminate. It can
reject the candidate or stop advertising enforcement until the necessary
context is available.

Enforcement is OPTIONAL. Relays SHOULD NOT silently strip non-conforming
events after accepting them.

## Security considerations

### Stolen authority key

A stolen NIP-72 owner key or NIP-29 relay key can publish maximally
permissive rules with a new timestamp. The rollback floor does not revoke
that authority and provides no protection against such a new document.
Recovery requires rotating the underlying community or relay identity
according to the applicable community NIP.

### Stale or censoring relays

Replaceable events can linger on relays that have stopped receiving updates.
Persistent rollback state protects a client only after it observes the newer
floor. A fresh client cannot infer a floor from a document it has never
seen. Clients SHOULD retain rules state and consult the community's preferred
relay set where applicable.

A NIP-29 group relay already controls acceptance into its relay-scoped
group. Signed rules make its stated policy inspectable, but cannot force the
relay to apply that policy honestly.

### Rule-driven content blocking

A community authority can use per-pubkey `deny` rules to silence dissent.
This is a property of owner-controlled forums, not something this NIP can
prevent. Clients SHOULD make the active rules visible so members can inspect
the policy and choose to leave or fork.

### WoT denial of service

WoT traversal can be expensive. Clients and relays SHOULD cap traversal cost
and cache results. Exhausting the cap makes the affected gate indeterminate;
it MUST NOT silently become a pass.

### Quota history

Clients with partial history can undercount posts. Client-side quota checks
are therefore advisory unless backed by complete community history. Relay
enforcement is limited by that relay's own retained history, and independent
relays are not expected to reach identical quota verdicts.

## Mapping from ZeroNet `permission_rules`

This NIP is informed by ZeroNet's `content.json` `user_contents` feature:

| ZeroNet | This NIP |
| ------- | -------- |
| `permission_rules.".*".max_size` | `max_event_size` tag |
| `permission_rules.".*".files_allowed` | `k` tag list |
| `permission_rules."bitid/.*@zeroid.bit".max_size` | Deferred, see Open Issues |
| `permissions."bad_user@zeroid.bit": false` | `p` tag with `deny` |
| `cert_signers` | `wot` tag |

## Open issues

- **Per-author-pattern overrides.** ZeroNet uses regex patterns over
  `bitid/<id>@<cert-issuer>`. Nostr identities are flat pubkeys, and a
  per-pubkey `p` tag does not scale to large allowlists. A future revision
  could add per-author size overrides without changing the evaluation order.
- **Cross-relay quota replication.** This NIP deliberately does not define
  a consensus or replication protocol for quota histories. Deployments that
  need consistent quotas across relays need a separate history-sharing
  mechanism.
