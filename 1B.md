NIP-1B
======

Network Abuse Reports
---------------------

`draft` `optional` `relay`

This NIP defines an event for the operator of a server to report probes and attacks on it: the source addresses, the targeted services, the tool used by the attacker and a small, safe sample of what was sent.

It serves two purposes:

1. **Defence.** An operator who notices an attack asks relays who else has seen the same user agent or the same requests, and blocks the reported sources before they arrive.
2. **Research.** Reports from many operators show what attackers are doing and how their tooling and addresses change, which may help to find out who is behind an attack.

A report has to be cheap to publish from a log watcher and easy to find for an operator who sees the same thing.

However, a report helps attackers too: it tells them they were noticed. The report leaves out information that could further aid them, see [Privacy and safety](#privacy-and-safety).

## Terms

- A **reporter** is the software, or the person, that publishes reports about attacks on a server it runs.
- A **consumer** reads reports and decides what to do with them.
- An **attack** is any unwanted attempt on a server, from a probe of what it runs to the use of a vulnerability.
- A **source** is an address an attack came from.
- A **privacy network** is a service whose exit addresses are shared with many legitimate users, such as Tor or a commercial VPN.

## Abuse report

A network abuse report, from here on a report, is an addressable event of kind `31984`.[^addressable]

[^addressable]: **Why an addressable event?**
    So that a report can be updated under a stable identifier. An amended version with the same `d` tag replaces the old one, which is how a reporter adds what it saw later or removes a source. It also lets a reporter delete a report by replacing it with an empty one, on relays that do not honour a deletion request.

```jsonc
{
  "kind": 31984,
  "pubkey": "<reporter>",
  "created_at": 1794664041,          // when it is published, see "Time"
  "content": "",
  "tags": [
    ["d", "k3v9q2x7m4"],

    // who
    ["s", "203.0.113.", "7"],
    ["s", "198.51.100.", "23"],
    ["s", "2001:db8:5:17:", "0:0:0:a3"],
    ["c", "AS64500"],
    ["c", "AS64501"],
    ["i", "iso3166:NL"],

    // what
    ["w", "cpe:/a:wordpress:wordpress"],
    ["l", "T1110", "org.mitre.attack"],
    ["u", "curl/7.88.1"],
    ["o", "/xmlrpc.php", "POST", "HTTP/1.1"],
    ["o", "/wp-login.php", "POST", "HTTP/1.1"],
    ["o", "/?author=1", "GET", "HTTP/1.1"],

    ["expiration", "1802390400"]
  ]
}
```

Every report contains useful information on its own. See [Scope](#scope) for what one report covers.

| Tag          | Repeat | First value                            | Values after it       |
| ------------ | ------ | -------------------------------------- | --------------------- |
| `d`          | once   | opaque identifier                      |                       |
| `s`          | any    | block of a source address              | rest of the address, privacy network |
| `c`          | any    | autonomous system of a source          |                       |
| `i`          | any    | country of a source                    |                       |
| `w`          | 0 to 2 | application the attack was aimed at    | version               |
| `l`          | any    | vulnerability or kind of attack        | namespace             |
| `L`          | any    | namespace of a label, optional         |                       |
| `u`          | any    | user agent                             |                       |
| `o`          | any    | sample operation: for HTTP, the request target | HTTP method, protocol |
| `b`          | any    | callback host named in a request       |                       |
| `count`      | 0 or 1 | number of sources seen                 |                       |
| `a`          | any    | related report                         | relay, marker         |
| `r`          | any    | URL where the attack is documented     |                       |
| `observed`   | 0 or 1 | first seen                             | last seen             |
| `expiration` | 0 or 1 | [NIP-40](40.md) expiration             |                       |

A tag is its name followed by one or more values, as in `["o", "<request target>", "<method>", "<protocol>"]`. Relays index only the first value, so that is the one a consumer can search for.

A report MUST have a `d` tag. Everything else is optional.

The `d` tag is an opaque string chosen by the reporter, unique among its reports. It SHOULD NOT be derived from the name or address of the server.

A report MAY have `content`.

### Scope

A report generally describes a single event, such as an attack on a particular application. An ongoing attack SHOULD get a fresh report each day, counted from 00:00 UTC, which can link to the report of the day before, see [Related reports](#related-reports-a).

A reporter SHOULD report only crawls and attacks on services it actually runs, and leave out requests for software that is not on the server.[^own-services]

[^own-services]: **Why only services the reporter runs?**
    To keep reports high in signal. Every server gets a steady background of requests from scanners that try everything everywhere, not unlike the crawling of a search engine. Reporting it adds volume and little knowledge.

A report names one application in `w`. An attacker that goes after five applications results in five reports. Requests aimed at the server as such and at no application in particular, such as guesses at the names of configuration and backup files, share a report without `w`. A reporter MAY leave them out as background scanning.

Attempts at exploiting a specific CVE (or other documented vulnerability) get a report of their own. If the same application was also attacked in a different way, that goes in a separate report.

If different tools were deployed in the attack, they SHOULD be reported separately. But if user agents were simply randomized to evade detection, that does not count as separate tools.

A report can be about any service, not only a web server. The application in `w` tells which protocol was used, so there is no tag for it: `cpe:/a:bitcoin:bitcoin_core` indicates an attack on a Bitcoin node.[^cpe-name]

[^cpe-name]: **Where does this name come from?**
    It is the [name of Bitcoin Core](https://nvd.nist.gov/products/cpe/search/results?keyword=cpe:2.3:a:bitcoin:bitcoin_core) in the CPE dictionary of the National Vulnerability Database, which CVE records use to name software. See [Application](#application-w).

There is no tag for the identity of the attacker, because it is rarely known at the time of the attack. Once it is discovered, an event of another kind can link the attacker to the report. Which reports make up one campaign is likewise better worked out afterwards: a researcher can group reports by reporter, user agent and time.

### Sources: `s`, `c` and `i`

```
["s", "<block>", "<rest>", "<privacy network>"]
```

A source is the address the requests came from, written in two parts for easier search.[^split] Concatenate the two parts before parsing the address:

|      | Address             | `<block>`        | `<rest>`   |
| ---- | ------------------- | ---------------- | ---------- |
| IPv4 | `203.0.113.7`       | `203.0.113.`     | `7`        |
| IPv6 | `2001:db8:5:17::a3` | `2001:db8:5:17:` | `0:0:0:a3` |

- For IPv4, `<block>` is the first three numbers of the address, each followed by a dot: its `/24`. `<rest>` is the last number.
- For IPv6, `<block>` is the first four groups of the address, each followed by a colon: its `/64`. `<rest>` is the last four groups. Groups are in lower case hexadecimal without leading zeros, and `::` is not used, so that a `<block>` has only one spelling.
- `<rest>` MAY be `*`, as in `["s", "203.0.113.", "*"]`. The reporter then saw more than one address in `<block>` and does not list them one by one.
- `<rest>` MAY be an empty string, as in `["s", "203.0.113.", ""]`. The reporter then does not give the address. The value itself is never left out.
- An IPv4-mapped IPv6 address is reported as the IPv4 address.
- `<privacy network>` is one of the names under [Privacy networks](#privacy-networks). It is absent for a direct source.

[^split]: **Why is the address split in two?**
    Relays index only the first value of a tag and match it exactly. With the block first, a consumer who saw one address finds the reports about any address in the same block, and can then compare the addresses in those reports with the full address it saw. An exact match is not always what counts. The last 64 bits of an IPv6 address are an interface identifier ([RFC 4291](https://www.rfc-editor.org/rfc/rfc4291)), which a host may change over time ([RFC 8981](https://www.rfc-editor.org/rfc/rfc8981)). IPv4 prefixes longer than `/24` are generally not announced on the Internet ([RFC 7454](https://www.rfc-editor.org/rfc/rfc7454)), so the addresses of a `/24` belong to the same announced network.

```
["c", "AS<number>"]
```

A `c` tag names the autonomous system that announced a source **when the attack was seen**, so that reports can be found by network as well as by source. It is written as the letters `AS` and the number in plain decimal: `AS64500`.

```
["i", "iso3166:<country code>"]
```

An `i` tag names the country in which a source was located **when the attack was seen**, so that reports can be found by country as well.[^country] It is a [NIP-73](73.md) identifier: `iso3166:` followed by the two-letter [ISO 3166-1](https://en.wikipedia.org/wiki/ISO_3166-1) code in upper case, as in `iso3166:NL`. A reporter MAY also name a subdivision of the country by its ISO 3166-2 code, as in `iso3166:US-CA`. Such a report SHOULD carry the tag for the country as well, `iso3166:US-CA` and `iso3166:US`, so that both can be searched for.

The country is where the machine that sent the requests is thought to be, not where the attacker is. A reporter leaves the tag out for a source whose country it does not know.

[^country]: **Why give the country when a consumer can look it up?**
    Searching reports by country may be useful, and a relay can only search what is in a tag. A later lookup may also give another answer.

A report MAY omit the autonomous systems of privacy network exits, see [Privacy networks](#privacy-networks). It SHOULD NOT give their countries, which say nothing about where the attack came from.

### Privacy networks

An exit address of a privacy network is shared by many people, and an attacker gets a new one at no cost. A report for every exit would cost relays space and add little. A report SHOULD only list the first address seen from any given privacy network. This effectively creates a distributed list, spread over many reports, which aids consumers that have no such list. It may also reveal that a particular exit is used more often than others.

So, for sources on a privacy network:

- A report MAY give the number of exits it saw in `count`. It SHOULD name the network in its `s` tag, as in `["s", "192.0.2.", "88", "tor"]`, so that no consumer mistakes it for the attacker's own address.
- A reporter SHOULD establish that an address is an exit from independent data, such as the exit list that Tor publishes, and not from other reports.
- The reporter MAY leave the exit address out and put the placeholder `192.0.0.8` in its place: `["s", "192.0.0.", "8", "tor"]`.[^placeholder] Consider doing so when the operator of a privacy network does not publish their exit addresses.
- The tag enables consumers to decide whether or not to (temporarily) block a particular exit, or even the entire privacy network.

A report MAY mix direct sources and exits.

A server that is reached from inside a privacy network, like a Tor hidden service, never sees where a request comes from. Its report uses the placeholder as the address and appends `-internal` to the name of the network: `["s", "192.0.0.", "8", "tor-internal"]`. This says that the attack happened on the network itself, and sets it apart from a report that leaves out the address of an exit.

Network names are lower case words joined by hyphens:

| Name           | Network                                            |
| -------------- | -------------------------------------------------- |
| `tor`          | Tor exit relays                                    |
| `i2p`          | I2P outproxies                                     |
| `vpn`          | a VPN whose provider the reporter does not know    |
| `test-service` | a public service that sends requests for its users |

Any other network is named after itself, for example `icloud-private-relay` for Apple iCloud Private Relay. This NIP keeps no list of such names. A reporter SHOULD use the name it sees for that network in the reports of others.

`test-service` is for services that fetch a URL for anyone who asks, such as a reachability check from many countries. They are not privacy networks, but their addresses are not the attacker's, and others use them for honest purposes. Whether their requests count as abuse is a grey area. The reporter marks them with the name in the `s` tag, and the consumer decides.

### Application: `w`

`w` names the application the requests were made for, as a [CPE](https://nvd.nist.gov/products/cpe) name in its URI form, with the part, the vendor and the product and nothing after them: `cpe:/a:wordpress:wordpress`, `cpe:/a:apache:http_server`, `cpe:/a:forgejo:forgejo`.[^cpe]

[^cpe]: **Why CPE names?**
    CVE records name the affected software this way, so a report and a vulnerability can be matched by name.

A report reveals that the reporter runs the application it names. A reporter MAY add the version as a second value, as in `["w", "cpe:/a:wordpress:wordpress", "6.4.3"]`. The first value stays the same for every reporter, so that it can be searched for. A report SHOULD NOT reveal what the attacker does not already know, but much software announces its version anyway.

An application that the dictionary does not list is named by the domain name of the project that makes it, reversed and in lower case: `space.mempool` for the software of `mempool.space`, wherever the reporter runs it.

A plugin or other component has a name of its own. A report names it only when the attack is aimed at that one component, and then carries a second `w` tag for the application it belongs to, so that both can be searched for. A bulk plugin scan is an attack on the application, and its report names the application alone. A report SHOULD NOT reveal plugins whose presence is not obvious from the public website.

### Vulnerability and kind of attack: `l`

These two are [NIP-32](32.md) labels: an `l` tag with the value and its namespace.

```
["l", "<value>", "<namespace>"]
```

| Namespace          | Value                                    | Example               |
| ------------------ | ---------------------------------------- | --------------------- |
| `cve`              | a CVE identifier                         | `CVE-2021-41773`      |
| `ghsa`             | a GitHub advisory identifier             | `GHSA-xxxx-xxxx-xxxx` |
| `org.mitre.attack` | a technique in MITRE ATT&CK              | `T1110`               |
| `nip-1b`           | a kind of abuse that ATT&CK does not have | `crawl`              |

An `L` tag with a namespace is optional. Relays do not index the namespace in an `l` tag, so `["L", "cve"]` is what lets a consumer fetch all reports involving any CVE.

The kind of attack is named by the identifier of a technique in [MITRE ATT&CK](https://attack.mitre.org/techniques/enterprise/). A report that names a sub-technique SHOULD also carry the technique it belongs to, `T1595.002` and `T1595`, so that both can be searched for.[^attack-ids]

[^attack-ids]: **Why ATT&CK identifiers and not plain words?**
    They are stable, maintained by others and already used by other systems that share attack data, such as CrowdSec, which also makes reports useful outside Nostr. Software can show a readable name beside the identifier.

Common examples:

| Identifier  | Name in ATT&CK                    | What it looks like                              |
| ----------- | --------------------------------- | ----------------------------------------------- |
| `T1595`     | Active Scanning                   | probing of any kind                             |
| `T1595.002`[^looking-or-acting] | Vulnerability Scanning | requests that check for a known weakness |
| `T1595.003` | Wordlist Scanning                 | guessing the names of files and directories     |
| `T1110`[^looking-or-acting] | Brute Force | repeated attempts to log in |
| `T1190`[^looking-or-acting] | Exploit Public-Facing Application | an attempt to use a vulnerability |
| `T1499`     | Endpoint Denial of Service        | requests meant to exhaust the server            |

[^looking-or-acting]: **When is a request an exploit attempt and not a scan?**
    What matters is the difference between looking and acting. Take a site with a `/login` page. A `GET` for it only looks, which is `T1595.002`. A `POST` to it acts, which is `T1190` (or `T1110` when it is one of many guesses at a password). It does not matter whether the sender expected the `POST` to work because it knew of a specific vulnerability, or was just trying at random.

ATT&CK has no technique for plain crawling or scraping, where pages are fetched in bulk and nothing is aimed at a weakness. This NIP introduces a dedicated label: `["l", "crawl", "nip-1b"]`. However, most crawling is background noise and may not be worth reporting.

A reporter picks the nearest of these, and leaves the label out when none fits.

### User agent: `u`

`u` holds the `User-Agent` header as received, with bytes outside printable ASCII written as `%XX`; unlike in a request target, a space stays a space. An empty string means the header was empty or missing. For a protocol other than HTTP it holds the name the client gives itself there, such as the user agent in the `version` message of a Bitcoin node. A value longer than 256 bytes is cut at 256 bytes.

A reporter SHOULD leave the tag out when the user agent contains something specific to the reporter, such as its domain name.

### Sample operations: `o`

An `o` tag holds an operation that a source carried out, as a sample of what it sent. The part most worth searching for is its first value.

For HTTP an operation is a request:

```
["o", "<request target>", "<method>", "<protocol>"]
```

For example:

```
["o", "/xmlrpc.php", "POST", "HTTP/1.1"]
```

That is the tag for the line that nginx logs as

> 203.0.113.7 - - [14/Nov/2026:09:12:44 +0000] "**`POST`** /blog/**`xmlrpc.php`** *HTTP/1.1*" 404 153 "-" "curl/7.88.1"

on a server that has its blog under `/blog/`. The status, the size, the referrer and the time are not part of it.

The target is normalized so that the same request reported from two servers gives the same string:

1. Remove the scheme and host if the request line had them and they name this server. Keep them if they name another host, as in a probe for an open proxy.
2. Remove the path prefix under which the application is installed on this server, so that the path is relative to the root of the application.
3. Replace values that are specific to this server with a placeholder: `{self}` for its host names and addresses, `{user}` for the names of its accounts, `{id}` for identifiers of its content and `{secret}` for tokens and keys.
4. Keep the rest byte for byte, including upper and lower case and the percent-encoding the attacker chose. Write bytes outside printable ASCII, and the space, as `%XX` with upper case hexadecimal digits.
5. Cut a target longer than 512 bytes at 512 bytes and append `{cut}`.

Rules 1 and 2 do not apply to a target that is not a path: the `*` of an `OPTIONS` request, or the `host:port` of a `CONNECT`.

The method is in upper case. The protocol is the version from the request line and MAY be left out.

The `o` tags are a **sample**. A report SHOULD NOT list every request, so that neither the presence nor the absence of a request reveals how the server answered it.

How many to include is up to the reporter, within the limits under [Size](#size). Reporters pick the sample from the safest requests they saw:

- Prefer requests that are already widely known, such as the paths every scanner tries.
- Prefer requests without parameters over requests with them.
- Leave a request out when it cannot be made free of server-specific values.

For a protocol other than HTTP, the first value is whatever is most worth searching for there, such as the name of the P2P message for the Bitcoin protocol: `["o", "addr"]`. Any further values are left to those who report on that protocol.

When the attack uses a known vulnerability, the reporter SHOULD leave out the requests.[^known-vulnerability]

[^known-vulnerability]: **Why leave out the requests for a known vulnerability?**
    Either the record of the vulnerability documents how it is exploited, and repeating that adds nothing, or it does not, and there is a good reason for that.

When a reporter believes an attack uses a vulnerability for which no fix has been released, it SHOULD NOT publish a report of that attack at all. The operator of the server SHOULD wait for a public announcement about it (or, if possible, responsibly disclose the issue to the maintainers of the application).

Reports MAY be published after a delay, with the time of the attack in `observed`, once doing so is responsible.

### Callback hosts: `b`

Some requests name a host that the attacked server is meant to contact, to fetch something from it or to let the attacker know that the request worked. A `b` tag holds such a host: `["b", "callback.example.net"]`.

- The value is a host name in lower case, or an IP address: IPv4 in dotted decimal form, IPv6 as in [RFC 5952](https://www.rfc-editor.org/rfc/rfc5952). An internationalized name is written in its ASCII form, with `xn--` labels ([RFC 5890](https://www.rfc-editor.org/rfc/rfc5890)). The scheme, the port and the path are left out.
- A reporter leaves out what cannot be a real host on the Internet: a name that is not well formed, a name under `.example`, `.invalid`, `.test`, `.local` and the like, a private or loopback address, one of its own hosts, and a name that was made only to reach such an address. A well-formed name that does not exist is explicitly allowed: whether a domain exists is sometimes used as a command and control signal.
- A reporter SHOULD NOT look the name up or contact the host.
- A reporter SHOULD leave a host out when it does not look safe to pass on, or cut the unsafe part and write `{cut}` in its place: `{cut}.example.net`.
- A reporter SHOULD likewise leave out a host that refers to the reporter itself, or write `{self}` in place of that part: `{self}.example.net`.
- A reporter SHOULD leave out a host that clearly has nothing to do with the attack, for instance a well-known site that the request merely mentions and that cannot relay a message to the attacker.
- The host may come from a part of the request that the report does not show, such as its body.

A consumer SHOULD NOT assume that a callback host belongs to the attacker. It may be a public service that anyone can use, a machine taken over from somebody else, or a name put there to mislead.

### Number of sources: `count`

`["count", "<number>"]` MAY give the number of distinct sources the reporter saw take part in what the report is about.[^not-requests] It is useful when the report lists fewer than that.

[^not-requests]: **Why not the number of requests?**
    It could reveal that an attack was blocked after a single attempt. Attack outcomes should not be reported.

### Related reports: `a`

```
["a", "31984:<pubkey>:<d>", "<relay>", "<marker>"]
```

A report MAY point at other reports that the reporter believes are about the same attack: the report of the day before when an attack goes on, or the other parts when one attack did not fit in one report. `<relay>` MAY be an empty string. A relay SHOULD accept a report without having the reports it points at.

Pointing at one report relates a report to everything that report points at in turn.

`<marker>` is absent or `sources`. With `sources`, the tag says where to find the sources that the report does not list itself:

- `count` gives the number of sources that took part in what the report is about.
- The `s` tags list only the sources that are new.
- The others are among the sources listed by the reports that are pointed at with the marker, and by the reports those point at with it in turn.

This is for an attack with more sources than fit in one report. A report of a smaller attack SHOULD list all its sources, so that it is useful on its own, and point at earlier reports without the marker. A source that is left out keeps the expiration of the report that lists it.

### Outside references: `r`

```
["r", "<URL>"]
```

A report MAY point at a page outside Nostr where the attack is documented, such as its entry on a tracking platform or a write-up.

### Time

`created_at` is the time the report is published.

A report that appears right after a request tells the attacker which server published it and how quickly it noticed. Rounding `created_at` would not prevent that, since a relay and everyone subscribed to it see when an event arrives. Reporters therefore SHOULD wait before they publish, for a random time or until a fixed time of day. The same goes for amended versions of a report.

`["observed", "<first seen>", "<last seen>"]` gives the times at which the sources were first and last seen attacking, as Unix timestamps. `<last seen>` MAY be left out when it is the same. Without an `observed` tag, `created_at` stands in for it. An exact time likely matches a line in the attacker's own records, so a reporter MAY round the two times to 00:00:00 UTC: the first down, the last up.

### Expiration

Reports SHOULD carry a [NIP-40](40.md) `expiration` tag, 90 days after the sources were last seen.

Most single addresses leave an attacker's hands well within 90 days.[^lifetimes] The longer time is for malicious autonomous system operators, whose networks stay bad for months. It also gives researchers time to work with a report before it is gone. That holds for a report that lists an exit of a privacy network as well. The distributed list of exits described under [Privacy networks](#privacy-networks) then follows the real network with some delay.

[^lifetimes]: **How long does a source stay in an attacker's hands?**
    Days for most addresses, months for networks:
    - Public blocklists remove an address after nine days on average, and 42% of addresses within two days ([Ramanathan et al., IMC 2020](https://doi.org/10.1145/3419394.3423657)).
    - 29% of blocklisted addresses are listed again after their removal, in 91% of cases within 30 days ([Ramanathan et al., NDSS 2020](https://www.ndss-symposium.org/ndss-paper/blag-improving-the-accuracy-of-blacklists/)).
    - Apart from research scanners, few addresses that scan the Internet ever come back to scan again ([Griffioen et al., IMC 2024](https://doi.org/10.1145/3646547.3688409)).
    - Network blocks used by bulletproof hosting services last a few months, 121 days on average at data centres ([Alrwais et al., IEEE S&P 2017](https://www.ieee-security.org/TC/SP2017/papers/166.pdf)).
    - More than 40% of the command and control addresses on three malware feeds were still listed two years later ([Li et al., USENIX Security 2019](https://www.usenix.org/conference/usenixsecurity19/presentation/li)).

### Size

Relays limit the size of an event and the number of its tags. These limits are not standard: each relay sets its own, and may announce them in its [NIP-11](11.md) document as `max_message_length` and `max_event_tags`. A report may later be passed on to relays other than the one it was first sent to, so it SHOULD stay well below the common limits: under 32 kB and fewer than 1024 tags.[^limits]

[^limits]: **Where do these numbers come from?**
    They are half of the defaults of [strfry](https://github.com/hoytech/strfry/blob/master/strfry.conf), software that many relays run: 65,536 bytes for an event and 2,000 tags.

How to divide the tags between sources, user agents and sample requests is up to the reporter. A reporter SHOULD include every source address if space allows, but MAY write a block once, with `*` as the rest, in order to stay below these limits. It can then give the number of sources it saw in `count`. What still does not fit goes in another report.

## Amending and deleting a report

If an attack continues on the same day after it is reported, reporters SHOULD publish an amended version, with the new time last seen and an expiration 90 days after that.

If what was reported turns out not to have been an attack, the reporter SHOULD delete the report.

If a source turns out to be a false positive, the reporter SHOULD publish an amended version of the report without it.

If the reporter believes that a source has been cleaned (it was itself a victim, for example a compromised machine or an open proxy), it SHOULD amend the report as well. It MAY keep what the report says about the attack and put a placeholder where the address was: `["s", "192.0.0.", "8"]` for an IPv4 source and `["s", "100:0:0:1:", ""]` for an IPv6 source.[^placeholder] Its autonomous system SHOULD be kept in a `c` tag, and its country MAY be kept in an `i` tag, as they still say where the attack came from. Consumers SHOULD NOT block a placeholder.

[^placeholder]: **Why these addresses as placeholders?**
    They are the IPv4 dummy address ([RFC 7600](https://www.rfc-editor.org/rfc/rfc7600)) and the dummy IPv6 prefix ([RFC 9780](https://www.rfc-editor.org/rfc/rfc9780)) in the IANA registries of special-purpose addresses. Neither is routed on the Internet, so a consumer that blocks one by mistake blocks nobody. `0.0.0.0` and `::` were not used because some tools read them as "any address".

To **delete** a report, the reporter sends a [NIP-09](09.md) deletion request with an `a` tag for the report and `["k", "31984"]`. As not every relay honours deletion requests, it SHOULD first publish an amended version that has only the `d` tag. Consumers SHOULD ignore such an empty report and drop what they held under that address.

Consumers that keep a block list built from reports SHOULD drop a source when the report it came from is replaced without it, is deleted, or expires.

## Privacy and safety

The attacker knows which addresses it used against which server. A report that lists them reveals which server the reporter's key belongs to, however long the reporter waits. Reporters SHOULD assume that the key and the server can be linked, and use a key that is not otherwise tied to a person if that matters.

A reporter MAY change its key as often as it likes, even for every report. Consumers MAY judge how reliable a report is by the reputation of its key. A reporter that changes keys MUST keep each old key until its reports have expired, so that it can still amend or delete them.

A report SHOULD NOT contain, in tags or in `content`:

- response status codes, response sizes, or any other sign of whether a request succeeded: a label for the kind of attack states what was attempted, not whether it worked;
- what the reporter did about the attack, such as whether and when it blocked a source;
- request bodies, cookies, and headers other than the user agent, the referrer among them;
- the reporter's host names, addresses and installation paths, and software versions that the attacker cannot see for itself;
- the timing of single requests.

### Text chosen by the attacker

A user agent, a request target and a callback host are text that the attacker chose, and a report carries it to everybody who reads the report. An attacker can use that to have text run or shown (terminal control codes, markup, part of a command or a query), to put a message, a link or somebody's name in front of readers, to cast suspicion on an unrelated host or a well-known crawler by naming it, or to identify the reporter, by sending each server a different text and seeing which one a report repeats.

The format limits this. These three tags hold printable ASCII only, each has a maximum length, and a callback host is a bare host name or address. Beyond that:

- A reporter SHOULD leave out a user agent, a request or a callback host that looks made to be read by people and not by a server.
- A reporter SHOULD check these values for its own host names and addresses, also where they are encoded. An attacker often puts the name or address of the server it attacks in a request, for instance as the callback host, and a report that repeats it reveals who published it.
- A consumer MUST treat these values as data from an unknown party, and never pass them to a shell, a query or a page without escaping them. It SHOULD NOT fetch what they name, or look up or contact a callback host.

## Consumers

A consumer that has spotted an attack by its user agent asks for the reports that mention it:

```json
["REQ", "sub", {"kinds": [31984], "#u": ["curl/7.88.1"], "since": 1794441600}]
```

Other useful filters are `#s` for the block of a source, `#c` for an autonomous system, `#i` for a country, `#w` for an application, `#l` for a vulnerability or a kind of attack, `#o` for a request target, `#b` for a callback host, `#a` for the reports that point at a given report and `#r` for those that point at a given page. Tags given together narrow the result: `"#w": ["cpe:/a:wordpress:wordpress"], "#c": ["AS64500"]` returns the reports of attacks on WordPress from that network.

From the reports it trusts, the consumer collects the sources. It can block the sources alone, the networks around them, or a whole AS when enough of the sources fall within it.

Anyone can publish a report, about any address. A false report is a way to get an innocent address blocked. Consumers therefore:

- SHOULD act only on reports from reporters they have chosen to trust, for instance the pubkeys they follow, a [NIP-51](51.md) follow set kept for this purpose, or the authors admitted by a relay they trust;
- SHOULD keep a list of addresses they never block, starting with their own;
- SHOULD give more weight to recent reports, because most sources move on within days;[^lifetimes]
- SHOULD prefer blocks that end by themselves;
- MAY require that several trusted reporters name a source before acting on it.

## Relays

A relay that accepts network abuse reports SHOULD support deletion requests ([NIP-09](09.md)) and expiration ([NIP-40](40.md)).

Which reports a relay accepts, and who may read them, is up to the relay, as for any other event.
