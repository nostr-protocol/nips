NIP-F8
======

Visit Counter
-------------

`draft` `optional` `relay`

This NIP defines how clients report a visit to an addressable event and how a relay publishes signed, hourly visit statistics for it, visible only to the author of the content.

## Motivation

Content creators want to know how many people read their work. Counting in each client fragments the number and storing one event per visit grows the relay database without bound. Here the relay counts, deduplicates and publishes only aggregates, signed with its own key and delivered only to the author.

## Visit event (`kind:20918`)

An ephemeral event sent by any client (Nostr client or web page) when content is opened.

```jsonc
{
  "kind": 20918,
  "pubkey": "<visitor pubkey>",
  "created_at": <unix timestamp>,
  "tags": [
    ["a", "<kind>:<author pubkey>:<d-tag>"]
  ],
  "content": "",
  // ...
}
```

- The event MUST have exactly one `a` tag identifying the visited content (the *target*).
- Clients without a user key MAY generate a random key and keep it locally to sign visits.
- Being ephemeral, the relay MUST NOT store it and SHOULD NOT broadcast it to subscribers.

## Counting rules

The relay counts a visit to *target* during clock hour *H* (UTC, truncated to the hour) only if:

1. the visit `pubkey` is not the author pubkey of *target*;
2. within *H*, it has not already counted a visit to *target* from the same `pubkey`;
3. within *H*, it has not already counted a visit to *target* from the same source IP address.

Each counted visit increments the counter `(target, H)`. Deduplication state for an hour MAY be discarded once the hour ends. The relay replies `OK true` whether or not the visit was counted, so clients cannot probe the deduplication state.

## HTTP visit (optional)

Some clients render content without running scripts or signing events, but still load images. A relay MAY expose:

```
GET /visit?a=<kind>:<author pubkey>:<d-tag>
```

on the same host as its websocket endpoint. Content authors embed it as an image. The relay counts the visit with the same rules, using only the source IP address for deduplication, and always responds with a transparent 1x1 PNG and `Cache-Control: no-store`, whether or not the visit was counted or the address was valid.

## Statistics event (`kind:30918`)

An addressable event signed by the relay key. Two forms share the kind and differ by `d` tag. Both carry a `p` tag with the author pubkey of the target.

### Daily

```jsonc
{
  "kind": 30918,
  "pubkey": "<relay pubkey>",
  "tags": [
    ["d", "<target>:<YYYY-MM-DD>"],
    ["a", "<kind>:<author pubkey>:<d-tag>"],
    ["p", "<author pubkey>"],
    ["day", "YYYY-MM-DD"],
    ["total", "<visits in the day>"],
    ["hour", "00", "<visits>"],
    ["hour", "13", "<visits>"]
    // only hours with visits > 0
  ],
  "content": ""
}
```

### Total

```jsonc
{
  "kind": 30918,
  "pubkey": "<relay pubkey>",
  "tags": [
    ["d", "<target>"],
    ["a", "<kind>:<author pubkey>:<d-tag>"],
    ["p", "<author pubkey>"],
    ["total", "<all-time visits>"]
  ],
  "content": ""
}
```

The relay republishes the daily event of the current day and the total event after counting a visit. Days are in UTC.

## Privacy

Statistics belong to the author. The relay MUST deliver `kind:30918` events only to a connection authenticated via [NIP-42](42.md) with the pubkey found in the event `p` tag, and MUST silently omit them from any other subscription.

## Trust

Statistics are only meaningful for the relay that signed them. The relay advertises its signing key in the `self` field of its NIP-11 document. Clients MUST ignore `kind:30918` events whose `pubkey` does not match the `self` key of the relay they are trusting.

## Client usage

```jsonc
// after NIP-42 AUTH as the author: last 7 days of an article
["REQ", "s", {"kinds": [30918], "authors": ["<relay pubkey>"], "#a": ["30023:<author pubkey>:<slug>"], "since": <now - 8 days>}]
```
