NIP-97
======

Persisted Delivery Confirmation
-------------------------------

`draft` `optional`

## Abstract

A relay's `OK` message (NIP-01) answers a different question than the one clients
generally treat it as answering. This NIP defines how a client can learn, in a
standard way, whether an event it published is still retrievable from a given relay —
and how relays can attest to that fact cheaply enough that doing so is not a burden.

## Motivation

NIP-01 requires a relay to answer an `EVENT` message with `OK`, where the third
parameter is `true` when the event "has been accepted by the relay". The
standardized prefixes for a negative result are `duplicate`, `pow`, `blocked`,
`rate-limited`, `invalid`, `restricted`, `mute` and `error`. All of them describe
what happened *at the moment of intake*.

Nothing in the protocol describes what happened *afterwards*. In practice this
produces a blind spot with three distinct failure modes, all of them
indistinguishable from success at the client:

1. **Accepted but not persisted.** A relay may answer `OK ... true` after an
   in-memory buffer, a queue, or a write that later fails. The event is gone; the
   client has a receipt for it.
2. **Persisted then pruned.** Retention policy, disk pressure, or an operator's
   decision removes an event weeks later. Nobody tells the author.
3. **Stored but not servable.** A relay that accepts writes for an event kind it
   will not return in a `REQ` answer is, for practical purposes, not storing the
   event. This is common and invisible: it has been observed that relays may accept
   and store events of a kind they never serve back.

The consequence is that a user cannot answer a basic question about their own
data: *where is it, actually?* The information needed to answer exists at the
relay, and the author has cryptographic means to ask for it, but there is no
agreed way to do so.

This matters most for the users who have the least ability to work around it.
A user who publishes to several relays — the normal case under NIP-65 — has no way
to know whether that redundancy is real or nominal.

## Design

Three small pieces, all optional, all backwards-compatible.

### 1. A new `OK` prefix: `persisted`

Relays that durably store an accepted event SHOULD answer with the prefix
`persisted`, to distinguish "I have this on disk" from the weaker "I accepted
this":

```
["OK", "<event-id>", true, "persisted:"]
```

A relay that cannot make that guarantee MAY keep answering with an empty message
as before. Clients MUST treat an empty message as *unknown*, never as *persisted*.

`duplicate:` (already covered by NIP-01) already implies persistence and needs no
change.

### 2. A retrieval proof: the `PROOF` message

A client may ask a relay to prove that it still holds specific events:

```
["PROOF", "<subscription-id>", "<event-id>", "<event-id>", ...]
```

The relay answers with one of:

```
["PROOF", "<subscription-id>", "<event-id>", true,  "<unix-timestamp>"]
["PROOF", "<subscription-id>", "<event-id>", false, "unknown: no such event"]
```

The timestamp is the relay's own clock at the moment it verified local storage.
It is an attestation, not a proof of past retention — a relay can lie, as it can
about anything. The value is that lying becomes a deliberate, signed, attributable
act rather than a silent omission.

A relay MAY batch multiple `PROOF` requests and MUST send at least one response
line per requested event id.

### 3. Optional attestation: kind `1797`

A relay that wishes to make its persistence claim auditable MAY publish a
self-signed event with the relay's own key:

```yaml
{
  "kind": 1797,
  "tags": [
    ["d", "<event-id>"],
    ["relay", "wss://relay.example.com"]
  ],
  "content": "<unix-timestamp>",
  // other fields...
}
```

This is a `kind:1797` (addressable range is avoided deliberately — see below)
regular event, one per attested event id, which the *relay* signs with the key it
advertises in its NIP-11 document. It allows a third party to check later whether
a relay ever claimed to hold an event, without trusting the client that asked.

Publishing is SHOULD-level and relays with high write volume will reasonably
decline to do it per event. It is included because it is the only mechanism here
that survives the relay going offline, which is precisely when a user most wants
to know what they had.

## Client behaviour

Clients SHOULD:

- Verify delivery after publishing, without user action, and surface the result.
- Distinguish three states per relay and event: `persisted`, `accepted-only`
  (bare `OK ... true`), and `absent` (relay reachable, `PROOF` returned `false`).
- Show the result as a per-relay list rather than a single score, because
  "5 of 8 relays hold this" is actionable and "published" is not.
- Re-check periodically for *addressable* and *replaceable* events, where the
  stored version may have been replaced by a newer one from another client.
- Treat a relay that does not implement this NIP as `unknown`, never as a failure.
  An unimplemented optional NIP must not make a working relay look broken.

Clients SHOULD NOT block publishing on the verification result. Verification is a
diagnostic, and a slow relay must not become a failure mode.

## Relay behaviour

Relays SHOULD:

- Answer `PROOF` for events they hold, and answer `false` for events they do not.
- Never answer `true` for an event held only in a cache with a defined eviction
  policy that does not guarantee the retention window claimed.
- Include the capability in their NIP-11 document under `supported_nips`
  (a `97` entry) and MAY advertise the retention window they commit to.

Relays MUST NOT interpret an unknown `PROOF`-style message as a protocol error
that closes the connection; per NIP-01 an unknown message type should be ignored.

## Why not reuse an existing kind or mechanism

`REQ` with `ids` is the obvious candidate and is insufficient on its own: it
conflates "the relay does not have it" with "the relay does not serve it", which
is exactly the distinction this NIP exists to make. A relay that accepts writes
for a kind and never returns it in a `REQ` would look healthy.

`count` (NIP-45) tells a client how many events match a filter; it does not say
which, and cannot attest to a specific event id.

## Rationale for the kind number

`1797` sits in the range NIP-01 defines as *regular* (events expected to be
stored), which is required here — an addressable event would be replaceable per
`d` tag and one attestation would overwrite another. The number is deliberately
far from the ranges in active use to avoid collision with proposals in flight.

## Security considerations

- **An attestation is not a proof.** A relay can answer `true` and delete the
  event one second later. This NIP makes the claim explicit and attributable; it
  does not make it trustworthy. Clients should present it as a claim.
- **Privacy.** `PROOF` reveals to a relay which events a client cares about,
  including events the client did not publish to it. Clients SHOULD query only
  relays they have published to, and SHOULD NOT send third-party event ids.
- **Load.** A naive client could flood a relay with `PROOF` requests. Clients
  SHOULD batch, SHOULD NOT re-verify an event more than once per retention window,
  and relays MAY `rate-limited:` the message as with any other.

## Reference implementation notes

The author maintains automated publishing to a set of relays and found this gap
by measurement rather than in theory: events reported as accepted by every
connected relay, of which a subset was later not retrievable from relays that had
returned `OK ... true`. A concrete observed case is recorded in the discussion
on PR #556 (zap receipts), where a payment that must have produced a receipt
produced none, and no mechanism existed anywhere in the stack to establish
whether that was a refusal, a loss, or a failure.
