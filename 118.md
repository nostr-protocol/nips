# NIP-118

## Nostr Double Ratchet Invites

In order to start a [NIP-117](./117.md) Nostr Double Ratchet session, Alice and Bob need to exchange ephemeral public keys and a shared secret.

In a Nostr Double Ratchet invite, Alice gives Bob her

- ephemeral public key, which is also used to respond to the invite on Nostr,
- shared secret, and
- Nostr identity public key, which is used to authenticate the exchange.

Public keys and the 32-byte shared secret MUST be encoded as 64 lowercase hex
characters in event tags and URL JSON.

### Nostr event

Publishing an invite event on Nostr allows other users to start a Double Ratchet session with you.

```typescript
{
  pubkey: inviterIdentityKey,
  content: '',
  tags: [
    ['d', `double-ratchet/invites/${uid}`], // uid: unique name for the invitation, e.g. "public"
    ['l', 'double-ratchet/invites'], // label, for listing all your invites
    ['ephemeralKey', inviterEphemeralKey],
    ['sharedSecret', sharedSecret]
  ],
  kind: 30078,
  created_at,
  id,
  sig
}
```

`l` is a [NIP-32](32.md) label tag that can be used to list your invites. We use this approach with [NIP-78](./78.md) application specific data kind `30078` in order to not bloat the event kind space and instead have a human-readable label.

### URL

Invites can be also shared privately, without requiring a Nostr event. This improves privacy, removing the public association between the inviter and response.

URL and QR code are often convenient ways to share privately, especially when the other user is not yet on Nostr. Format:

```typescript
const invite = { inviter, ephemeralKey, sharedSecret };
const json = JSON.stringify(invite);
const url = `https://example.com/#${encodeURIComponent(json)}`;
```

Encoding the invite into the URL hash ensures it's not sent to the server and logged by default.

`nostr:` URI scheme is another possible way to share invites, when we have native clients supporting the feature.

### Invite response

An invite acceptance is carried in a signed kind `1059` event whose content
decrypts **directly** to an unsigned kind `1060` rumor. This uses the routing
shape of a [NIP-59](59.md) gift wrap, but it is not a complete NIP-59 gift wrap:
there is no kind `13` seal between the outer event and the rumor.

#### Response payload and rumor

The invitee generates a fresh NIP-117 session key pair. The session public key is
encoded in a JSON payload and encrypted twice, in this order:

```typescript
const identityConversationKey = nip44.getConversationKey(
  inviteeIdentitySecretKey,
  inviterIdentityPublicKey
);

// This is the deployed payload shape. sessionKey is a 32-byte Nostr public key.
const payload = JSON.stringify({ sessionKey: inviteeSessionPublicKey });

// Inner layer: proves control of the invitee identity key to the inviter.
const identityCiphertext = nip44.encrypt(payload, identityConversationKey);

// Capability layer, applied second: proves possession of the shared secret.
const capabilityCiphertext = nip44.encrypt(
  identityCiphertext,
  hexToBytes(sharedSecret)
);

const rumor = {
  pubkey: inviteeIdentityPublicKey,
  kind: 1060,
  content: capabilityCiphertext,
  tags: [],
  created_at: Math.floor(Date.now() / 1000),
  id: ""
};
rumor.id = getEventHash(rumor);
```

Senders MUST emit the JSON object form containing `sessionKey`. Early
implementations sent the session public key as a raw decrypted string; accepting
that form is an optional compatibility measure, not part of this protocol.

#### Outer event

The rumor is encrypted directly to the inviter's ephemeral public key using a
random key pair that is used for exactly one response event and then discarded:

```typescript
const oneTimeSecretKey = generateSecretKey();
const oneTimePublicKey = getPublicKey(oneTimeSecretKey);
const envelopeConversationKey = nip44.getConversationKey(
  oneTimeSecretKey,
  inviterEphemeralPublicKey
);

const response = finalizeEvent({
  kind: 1059,
  content: nip44.encrypt(JSON.stringify(rumor), envelopeConversationKey),
  tags: [["p", inviterEphemeralPublicKey]],
  created_at: randomizedRecentTimestamp
}, oneTimeSecretKey);
```

The response MUST contain exactly one `p` tag whose value is
`inviterEphemeralPublicKey`. Other tags, such as a NIP-13 proof-of-work tag, MAY
be included. The event's `pubkey` is `oneTimePublicKey`; that key MUST NOT be
reused. The outer `created_at` MAY be randomized by up to two days into the past
to reduce timing correlation. If the invite was published as an event, the `p`
tag still allows the response to be associated with that public invite.

#### Processing a response

The inviter MUST verify the kind `1059` event's id and signature and require
exactly one matching `p` tag before decrypting it. The inviter then:

1. decrypts `content` using ECDH between the inviter ephemeral private key and
   the event's one-time `pubkey`;
2. parses the plaintext as a kind `1060` unsigned rumor with no tags, and verifies
   its recomputed id and `created_at` field;
3. decrypts the rumor content with the invite shared secret;
4. decrypts that result using ECDH between the inviter identity private key and
   the rumor's `pubkey`; and
5. parses `{ "sessionKey": "..." }` and validates `sessionKey` as a Nostr public
   key.

The identity-key layer authenticates the claimed invitee to the inviter. The
shared-secret layer demonstrates possession of the invite data; for a public
invite the secret is also public and provides separation rather than private
authorization. Authenticity of the invite itself comes from the signature on a
published invite event or from the trusted channel used to deliver a private URL.

After processing succeeds, the invitee initializes NIP-117 as the initiator using
its new session private key, and the inviter initializes it as the responder using
the inviter ephemeral private key. Both use the other party's session public key
and the invite shared secret.

The wire protocol does not make an invite or response single-use. Receivers SHOULD
deduplicate accepted response event ids before creating sessions. Invite expiry,
revocation, maximum-use limits, replay policy beyond deduplication, session
selection, and session storage are application policy outside this NIP.
