NIP-F5
======

Relay-Set Communities
---------------------

`draft` `optional` `relay`

This NIP defines communities that are **defined by signed events** and **served
by a set of independent relays**. Unlike [NIP-29](29.md) groups, whose access
rules live inside one relay and are signed with the relay's key, here the
roster itself is a deterministic function of owner-signed events. Any relay in
the set — and any client — computes the same roster from the same events, so
no single relay is load-bearing: a community survives the loss of any of its
relays without a replication protocol.

Relays never talk to each other. Clients fan writes out to every relay in the
set, merge reads, and carry events that a relay is missing to it
(_backfilling_).

## Conventions

- Keys are hex-encoded; `created_at` is per [NIP-01](01.md).
- Relays authenticate clients with [NIP-42](42.md).
- Direct messages use [NIP-17](17.md) (gift wraps, kind 1059).
- Blobs use [Blossom](96.md) servers (which may be the community relays
  themselves) and are referenced with [NIP-92](92.md) `imeta` tags.

## Community definition — kind 33500

A community is identified by its **address** `33500:<owner-pubkey>:<d>`, where
the author of the event is the owner and the `d` tag is a random 32-character
hex string (the community id).

Tags:

- `d` (required): 32-character lowercase hex community id.
- `name` (required): display name.
- `about`, `picture` (optional).
- `relay` (zero or more): the full `ws://`/`wss://` URL of each relay in the
  set, including the slug path (e.g. `wss://relay.example.com/mycircle`).
- `join_mode`: `closed` | `codes` (default) | `pyramid`.
- `removal_mode`: `reparent` (default) | `cascade`.
- `depth_max`: integer ≥ 0, default 3.
- `quota`: integer ≥ 0, default 10.

The definition is a parameterized-replaceable event. The **latest** definition
(in fold order, below) supplies all settings; its history is not retained.
The owner cannot be changed. All relays in the set MUST hold an identical
definition event; clients publish the same event to each.

The definition event is publicly readable: relays SHOULD allow unauthenticated
queries for kind 33500 so joiners can discover the relay set and name.

## Control events

Membership changes are expressed as regular events (kinds 9500–9513), signed
by the users performing the action. Every control event MUST carry an `a` tag
whose value is the community address (`33500:<owner>:<d>`) — with an optional
relay hint — and MUST NOT carry a NIP-70 `-` tag (any member may carry them
between relays, see "Backfilling").

| kind | name       | signer                    | tags                                        |
| ---- | ---------- | ------------------------- | ------------------------------------------- |
| 9500 | grant      | owner (admins); owner/admin (members) | `a`, `p`, `role`                |
| 9501 | remove     | owner or admin            | `a`, `p`                                    |
| 9502 | ban        | owner or admin            | `a`, `p`, optional `reason`                 |
| 9503 | unban      | owner or admin            | `a`, `p`                                    |
| 9510 | invite     | member with invite rights | `a`, `invite-key`, `max_uses`, `expiration`, `role` |
| 9511 | claim      | joiner                    | `a`, `e`, `proof`                           |
| 9512 | leave      | member                    | `a`                                         |
| 9513 | invite revoke | invite author, owner or admin | `a`, `e`                             |

### Grants (9500)

Grants add a pubkey as a member or set an existing member's role. `role` is
`admin` or `member`; `admin` MAY only be granted by the owner. Granting a
banned pubkey has no effect until they are unbanned. Grants addressed to the
owner MUST be ignored.

### Removal (9501) and bans (9502)

Removing a member honors the definition's `removal_mode`:

- `reparent`: the removed member's direct invitees are re-parented to the
  signer of the removal event; their depths do not change.
- `cascade`: the removed member and all their transitive invitees are removed.

A ban removes the target and marks them banned. Bans override grants and
claims. `unban` (9503) lifts a ban but does not restore membership. The owner
cannot be removed or banned. Removed members can always rejoin (by a new
grant or claim).

### Invites (9510), claims (9511) and revocation (9513)

An invite binds a one-time capability to an **ephemeral keypair**: the
`invite-key` tag holds the ephemeral *public* key, while the secret is
distributed out of band (e.g. inside an invite link). `max_uses` defaults to
1 and `expiration` (unix seconds) is optional. `role` defaults to `member`;
admin-role invites MAY only be minted by the owner.

In `pyramid` mode any member may mint member-role invites, subject to:

- `depth_max`: an invite by a member of depth *n* can only produce members of
  depth *n + 1* or less.
- `quota`: at most `quota` invites per member (revoked ones included).

A claim (9511) is published by the joiner with:

- `e`: the invite event id.
- `proof`: a 64-byte hex [BIP-340](https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki)
  signature by the invite's ephemeral key over
  `sha256("circlets-claim:" + <invite-event-id-hex> + ":" + <joiner-pubkey-hex>)`
  (ASCII, lowercase).

A claim is valid if, at its fold position, the invite exists, has uses left
and is not revoked, `created_at` is not past the invite's `expiration`, the
joiner is not banned and not already a member, and the depth limit still
holds (the invite signer's depth may have grown since the invite was minted).
Valid claims settle in fold order until `max_uses` is reached.

A revoke (9513) invalidates later claims on the invite; already-settled
claims stand. Claiming while already a member is allowed but has no effect
and consumes no use.

## The fold

The roster is a pure function of the definition and the set of control
events:

1. Sort events by `(created_at, event id)` ascending.
2. Apply each in order; an event that is invalid at its position (per the
   rules above) has no effect. The latest definition supplies all settings.
3. The result is the set of members (with role, depth and invite parent),
   the ban list, the per-invite claim settlement, and a per-pubkey
   membership **timeline** (used for backfill checks, below).

The fold MUST be implemented identically by relays and clients. Depth is 0
for anyone invited directly by the owner or an admin, and the invite parent's
depth + 1 otherwise; depth does not change on re-parenting.

Because ordering is `(created_at, id)`, events created within the same second
may reorder relative to their arrival. Clients performing rapid consecutive
actions (e.g. minting an invite and then claiming it) SHOULD use distinct
`created_at` values.

## Relay behavior

### Registration

A relay serves `wss://host/<slug>` for an unknown slug only to accept a
kind-33500 event whose `relay` tags include the URL the client connected to.
The slug MUST be validated and free. Operators can gate registration with an
allowlist of owner pubkeys and per-owner caps. Once stored, the community is
served at that path like any other.

### Acceptance rules

For events submitted **directly by their author**:

- Content kinds: the author must be an active member and `created_at` MUST
  NOT be more than 10 minutes in the future.
- Control kinds: `created_at` MUST be within 10 minutes of now, and the
  relay SHOULD evaluate the fold to return precise rejections (exhausted
  invites, not allowed, etc.). Events the fold rejects are not stored.

For events submitted by a **carrier** (authenticated pubkey ≠ author) —
"backfilling":

- The carrier must be an active member. Exceptions: kinds 9510 and 9511 may
  be carried by a non-member joiner (the invite bootstrap path).
- The author must have been an active member of this community at
  `created_at`, checked against the fold's membership timeline.
- `created_at` MUST NOT be in the future and MUST NOT predate the definition.
- Control events are stored even if the fold gives them no effect; the fold
  — never ingest — decides settlement.

Everything else is standard relay policy: per-pubkey rate limits, gift-wrap
broadcast restrictions (only the `p`-tagged recipient ever receives a 1059),
and [NIP-09](09.md) deletions of one's own events.

### Storage and discovery

Relays MUST NOT require membership tables: the roster is derived from the
event store. Relays SHOULD support [NIP-77](77.md) negentropy so clients can
efficiently discover and repair gaps. Relays SHOULD serve a public directory
(e.g. `GET /_directory` as JSON, or per-community NIP-11 documents extended
with the community address and relay list) so clients can discover
communities and their relay sets.

## Client behavior

Clients connect to **every** relay in the definition's `relay` list, using
per-relary reconnect with backoff. Events are deduplicated by id and all
signatures are verified locally (relays are not individually trusted).

Writes are fanned out to every relay; a write is considered successful when
at least one relay accepts it, and failures are retried from a persistent
outbox. Clients keep a local event store so they can (a) read offline,
(b) resume with `since` cursors per relay, and (c) re-seed a replacement
relay by backfilling what they hold.

The local fold drives everything user-facing: whether the user is a member,
the roster, moderation rights, and which relays to talk to. Relay `CLOSED`
messages are informational only.

Moderation UIs publish control events to the whole set: grants, removals
(honoring `removal_mode`), bans and unbans by owner/admins; invites are
minted with a fresh ephemeral keypair and shared as a link containing the
invite event and the ephemeral secret. The joiner's client connects to the
relay set, ensures the invite event exists on every relay (backfilling it if
necessary), then publishes the claim.

## Rationale

- **Why not NIP-29?** NIP-29 groups are bound to one relay: the access rules
  and the roster are relay-private state signed with the relay key, and
  moving a group requires the relay's cooperation. Here the roster is
  portable by construction, and adding a relay to a set is a client-side
  operation, not an operator project.
- **Why no `-` tags?** [NIP-70](70.md) protection (author-only publishing) is
  incompatible with member-carried backfill, which is the mechanism that
  keeps the set convergent. Within a members-only relay set, the
  author/carrier rules above subsume it: nobody outside the community can
  publish community events to anywhere, and inside it, replication is the
  point. Clients verify all signatures so a misbehaving relay cannot inject
  events.
- **Why ephemeral keys in invites?** The invite creator publishes only a
  public key to relays; the secret enables exactly one claim per use and can
  be shared through any channel without exposing the creator's key.

## Conformance

Because the roster is a fold, implementations must agree exactly. A conformance
suite should pin: grants and role transitions, invite minting limits
(depth/quota), claim settlement order, `reparent` vs `cascade` removals, ban
precedence, re-joining, and the membership timeline queries used for backfill
checks. Implementations are encouraged to share vector files between relay
and client test suites.
