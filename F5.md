NIP-F5
======

FIPS Transport capability for web browsers
------------------------------------------

`draft` `optional`

This NIP defines `window.fipsTransport`, an optional browser-side capability
that allows Nostr web applications to request user-consented HTTP and WebSocket
connections to FIPS-addressed services.

The capability is intended for FIPS-capable browsers, native application
wrappers, mobile apps with embedded web views and browser extensions that can
reach FIPS nodes through local or native networking.

The capability provides network reachability only. It does not provide Nostr
signing authority, user identity, repository access, relay membership, file
permissions or service authorization.

## Motivation

Many Nostr-adjacent services are discovered or used through URLs:

- relays use WebSockets as defined in [NIP-01](01.md);
- relay metadata uses HTTP as defined in [NIP-11](11.md);
- HTTP APIs may use Nostr authorization as defined in [NIP-98](98.md);
- Blossom uses HTTP media servers and signed Nostr authorization, as referenced
  by [NIP-B7](B7.md);
- Git and GRASP workflows may use repository, clone, relay and service URLs as
  described in [NIP-34](34.md);
- app handlers, app-specific data and file metadata may point users toward
  service endpoints.

Public `https://` and `wss://` endpoints work for public infrastructure, but
they are awkward for private group services, local machines, peer-to-peer file
sharing, self-hosted relays behind private addressing and FIPS-native services.

`window.fipsTransport` gives Nostr web apps a standard way to ask a trusted host
environment to reach those services.

## Non-goals

This NIP does not:

- define FIPS itself;
- define routing, discovery, encryption or naming inside FIPS;
- require browsers to implement FIPS natively;
- replace `window.nostr`;
- sign events or HTTP auth tokens;
- define relay, Blossom, GRASP, Git, storage or ACL behavior;
- require existing public relay or Blossom URLs to move to FIPS.

## Terminology

- **web application**: JavaScript application running in a browser or web view.
- **host environment**: browser, native wrapper, mobile app or extension
  exposing `window.fipsTransport`.
- **FIPS address**: an address string or URL whose scheme or authority is
  resolvable by the host environment's FIPS implementation.
- **permission grant**: user consent allowing a web origin to connect to a
  scoped FIPS target.
- **target**: a FIPS host, service, port, protocol or URL pattern.

## Relationship to FIPS

This NIP sits above the FIPS specification. The FIPS specification is
responsible for addressing, routing, encryption, peer discovery, connection
setup and native transport rules between FIPS nodes.

This NIP only defines the browser JavaScript contract that lets a Nostr web app
ask a FIPS-capable host environment to use that transport.

If the FIPS specification defines a canonical address or URL form, implementations
of this NIP SHOULD reuse it. If FIPS intentionally treats addresses as opaque
strings, implementations of this NIP SHOULD accept opaque FIPS address strings
and MUST NOT invent an incompatible addressing layer.

## Interface

A host environment MAY expose:

```ts
interface Window {
  fipsTransport?: FipsTransport;
}

interface FipsTransport {
  readonly version: string;
  readonly capabilities: {
    fetch?: boolean;
    websocket?: boolean;
    binaryBody?: boolean;
    streamingRequest?: boolean;
    streamingResponse?: boolean;
  };

  requestPermission(request: FipsPermissionRequest): Promise<FipsPermissionGrant>;
  revokePermission?(grantId: string): Promise<void>;
  listPermissions?(): Promise<FipsPermissionGrant[]>;

  fetch(input: FipsRequestInfo, init?: FipsRequestInit): Promise<FipsResponse>;
  openWebSocket(url: string, protocols?: string | string[], options?: FipsWebSocketOptions): Promise<FipsWebSocket>;
}
```

Plainly: `window.fipsTransport` is a small set of controls that a web page can
use when the host browser or application supports FIPS. The page does not learn
FIPS routing internals and does not receive any private keys. It can ask for
permission, make an HTTP-style request or open a WebSocket-style connection; the
host environment performs the FIPS connection behind the scenes.

## Discovery

Applications SHOULD check `window.fipsTransport` directly.

Host environments MAY dispatch:

```js
window.dispatchEvent(new Event("fips-transport-ready"));
```

Applications SHOULD support both direct detection and the readiness event,
because browser extensions may inject capabilities after page load.

## URL handling

This NIP does not define a new FIPS address format. It uses the canonical address
form from the FIPS specification.

When a URL-shaped representation is needed for browser APIs, a host environment
MAY use `fips://` as a browser-facing form, with the permission request naming
the intended application protocol:

```json
{
  "target": "fips://alice-laptop/files",
  "protocols": ["https"],
  "ports": [443]
}
```

Examples of URL-shaped FIPS targets:

```text
fips://<host>
fips://<host>:<port>/<path>
fips+wss://<host>:<port>/<path>
fips+https://<host>:<port>/<path>
```

These examples are not normative if the FIPS specification defines a different
canonical representation.

## FIPS endpoints in existing Nostr fields

FIPS endpoints SHOULD be allowed directly anywhere an existing Nostr spec already
accepts service URLs, provided clients that do not support this NIP ignore
unsupported schemes gracefully.

Parallel `fips` tags SHOULD NOT be added by default. They fragment every spec
that already has a URL field. Dedicated FIPS tags should be considered only when
an existing spec has strict URL scheme requirements, where legacy clients break
instead of ignoring unknown schemes, or where the FIPS endpoint is semantically
different from the public endpoint rather than merely a different transport
route.

## Permission requests

```ts
interface FipsPermissionRequest {
  target: string;
  protocols?: Array<"http" | "https" | "ws" | "wss">;
  ports?: number[];
  purpose?: string;
  duration?: "session" | "persistent";
  serviceHint?: "relay" | "blossom" | "grasp" | "git" | "storage" | "api" | string;
}

interface FipsPermissionGrant {
  id: string;
  target: string;
  origin: string;
  protocols: string[];
  ports?: number[];
  expiresAt?: number;
  serviceHint?: string;
}
```

The host environment MUST bind permission grants to the requesting web origin.
It MUST NOT allow one origin to reuse another origin's grant.

The host environment SHOULD show the user the requesting origin, target,
protocol or service and whether the grant is session-only or persistent.

The host environment SHOULD scope grants as narrowly as practical, including:

- origin;
- target host or address;
- protocol;
- port;
- session or account context;
- optional path prefix for HTTP services.

## HTTP transport

```ts
type FipsRequestInfo = string | {
  url: string;
  method?: string;
  headers?: Record<string, string>;
  body?: ArrayBuffer | Uint8Array | string | null;
};

interface FipsRequestInit {
  method?: string;
  headers?: Record<string, string>;
  body?: ArrayBuffer | Uint8Array | string | null;
  signal?: AbortSignal;
}

interface FipsResponse {
  url: string;
  status: number;
  statusText: string;
  headers: Record<string, string>;
  body: ArrayBuffer;
}
```

The minimum response contract is a plain serializable object with an
`ArrayBuffer` body. Browser-like `Response` wrappers are useful ergonomics, but
extension and native bridges are easier to implement reliably when the normative
shape is serializable.

Required behavior:

- `fetch()` MUST require an applicable permission grant before connecting.
- `fetch()` MUST support at least `GET`, `HEAD` and `POST`.
- implementations MUST support binary response bodies;
- implementations SHOULD support binary request bodies, `PUT`, `DELETE` and
  range requests;
- implementations MUST allow application-provided headers except those the host
  environment blocks for security;
- implementations MUST return response status, headers and body without
  rewriting service semantics;
- implementations SHOULD support `AbortSignal`.

[NIP-98](98.md) and Blossom authorization are application-layer concerns. The
application signs with `window.nostr` or another signer, then passes
`Authorization: Nostr ...` through `fipsTransport.fetch()`.

## WebSocket transport

```ts
interface FipsWebSocketOptions {
  signal?: AbortSignal;
}

interface FipsWebSocket {
  readonly url: string;
  readonly readyState: number;
  send(data: string | ArrayBuffer | Uint8Array): void;
  close(code?: number, reason?: string): void;
  addEventListener(type: "open" | "message" | "error" | "close", listener: EventListener): void;
  removeEventListener(type: "open" | "message" | "error" | "close", listener: EventListener): void;
}
```

Required behavior:

- `openWebSocket()` MUST require an applicable permission grant before
  connecting;
- it SHOULD preserve WebSocket message ordering;
- it MUST support text messages;
- it SHOULD support binary messages;
- it MUST NOT inspect, alter, sign or synthesize Nostr relay messages.

[NIP-01](01.md) and [NIP-42](42.md) remain application and relay behavior above
the transport.

## Streaming

FIPS handles the lower-level connection after the host opens it, but this
browser API still needs to define what web apps can rely on.

Binary request and response bodies are required in version 1. Streaming request
and response bodies are optional capabilities. Large Git packs, media files,
backups and file transfers will benefit from streaming, but making streaming
mandatory in the first version would raise the implementation bar for browser
extensions and native wrappers.

Implementations that support streaming SHOULD advertise it through
`capabilities.streamingRequest` and `capabilities.streamingResponse`.

## Lifecycle

The host environment MUST close or invalidate connections when:

- the user revokes permission;
- the browser origin loses permission;
- the host account or session context changes in a way that invalidates the
  grant;
- the host FIPS identity or route binding changes in a way that makes the target
  ambiguous.

Applications SHOULD treat connection failure as ordinary transport failure and
SHOULD NOT fall back from a FIPS URL to a public proxy unless the user explicitly
chose that behavior.

## Security requirements

The host environment:

- MUST require explicit user consent before connecting to a FIPS target on
  behalf of a web origin;
- MUST bind grants to origin;
- MUST separate transport permission from signing authority;
- MUST NOT expose private FIPS keys or routing secrets to the page;
- MUST NOT expose Nostr private keys;
- MUST NOT grant access to local network or FIPS services outside the approved
  target scope;
- SHOULD make persistent grants reviewable and revocable;
- SHOULD show useful diagnostics when a target is unreachable or denied;
- SHOULD prevent silent fallback to public CORS proxies for FIPS URLs.

The web application:

- MUST use `window.nostr`, [NIP-46](46.md), [NIP-55](55.md) or another signer
  for Nostr signatures;
- MUST NOT assume a successful transport connection implies user identity or
  remote authorization;
- SHOULD request the narrowest useful permission;
- SHOULD display service authorization failures separately from transport
  failures.

The remote service remains responsible for NIP-42, NIP-98, Blossom
authorization, repository membership, ACLs, quotas, rate limits and
application-specific permissions.

## Example flows

### Private relay

1. A Nostr event or user setting references `fips://group-relay`.
2. The web app detects `window.fipsTransport`.
3. The app requests WebSocket permission for `fips://group-relay`.
4. The host prompts the user.
5. The app opens a WebSocket through `fipsTransport.openWebSocket()`.
6. The app speaks normal NIP-01 and NIP-42 over that connection.

### Private Blossom server

1. A user publishes a Blossom server list including a FIPS-addressed server.
2. A client needs to fetch or upload a blob.
3. The app asks for HTTP permission to the FIPS server.
4. The app signs any required Blossom or Nostr authorization with
   `window.nostr`.
5. The app sends the HTTP request with `fipsTransport.fetch()`.
6. The server enforces Blossom behavior and authorization as usual.

### Git or GRASP

1. A client reads a NIP-34 repository announcement or GRASP server list.
2. The announcement points to a FIPS-addressed GRASP or Git service.
3. The client requests permission for the target.
4. The host connects through native FIPS networking.
5. The client uses normal application logic for repository discovery, refs,
   packs and file browsing.
6. Identity and access remain separate through Nostr signatures and service ACLs.
