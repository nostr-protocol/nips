NIP-5E
======

Aggregate Queries
-----------------

`draft` `optional` `relay`

Relays may support the verb `SELECT`, which evaluates [JMESPath](https://jmespath.org/specification.html) expressions over the events matching a filter and returns grouped aggregates instead of the events. Salted samples let clients merge results from overlapping relays and check them against the relay's `REQ`.

The column `{"count": "id"}` answers the same question as a [NIP-45](45.md) `COUNT`, and `{"distinct": "pubkey"}` gives the exact count that NIP-45's HyperLogLog approximates.

## Request

```
["SELECT", <id>, <filters>, <columns>, <options>]
```

- `<filters>` is a non-empty array of [NIP-01](01.md) filters.
- `<columns>` is a non-empty array. A string is a grouping column, whose values split events into rows. An object with one key is an aggregate column. Its key is `count`, `sum`, `min`, `max` or `distinct`, and its value is an expression.
- `<options>` is an optional object:
  - `where` is an expression. Events for which it is falsy are skipped.
  - `latest` is an expression. Only the newest event for each of its values is kept.
  - `order` is `[<column index>, "asc" | "desc"]`.
  - `limit` is the maximum number of rows, applied after `order`.
  - `salt` and `sample` request [samples](#samples).

## Expressions

Expressions are evaluated against the event as a JSON object. For example, `tags[?[0]=='t'][1]` gives the values of all `t` tags. All JMESPath functions are available, plus:

- `from_json(string)` returns the parsed value, or null if the string is not valid JSON.
- `bolt11(string)` returns `{msats, payment_hash, description_hash, created_at}` from a [BOLT 11](https://github.com/lightning/bolts/blob/master/11-payment-encoding.md) invoice without checking its signature, or null if the string is not an invoice. `msats` is null if the invoice has no amount.
- `bucket(number, size)` returns `number` rounded down to a multiple of `size`.

Relays reject requests whose expressions do not parse, call unknown functions, or exceed the relay's size limits. An expression that fails at runtime is null for that event. Two values are equal when their [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) canonical JSON is equal.

## Evaluation

1. The relay selects the events it would return to a `REQ` with the same filters, under the same access rules and `search` semantics, but without its usual cap on results. A filter's `limit` selects that filter's `limit` newest events. An event that matches several filters is selected once.
2. Events for which `where` is falsy are dropped.
3. If `latest` is present, only the newest event for each of its values is kept. Ties go to the lowest id.
4. Each grouping column puts an event in one group, or in one group per distinct element if its value is an array. The event contributes to every combination of its groups.
5. Each row's aggregates are computed over the events that contribute to it:

   | Aggregate      | Value                                                                       |
   | -------------- | --------------------------------------------------------------------------- |
   | `count`        | The number of events whose value is not null                                |
   | `sum`          | The sum of the integer values, or 0                                         |
   | `min`, `max`   | The smallest or largest numeric value, or null                              |
   | `distinct`     | The number of distinct non-null values, counting each element of an array   |

   Integers above 2^53 − 1 are written as decimal strings.

6. A row lists its values in column order. Without grouping columns, there is exactly one row.
7. If `order` is present, rows are sorted by that column. Numbers sort numerically, and so do sums written as strings. Other strings sort by code point, and nulls sort last. Then the first `limit` rows are kept.

## Response

```
["SELECT", <id>, <rows>]
["SELECT", <id>, <rows>, <samples>]
```

The second form answers requests with `sample`. A relay that refuses a request, for example because it selects too many events or takes too long, MUST respond with `["CLOSED", <id>, <reason>]`.

## Samples

When `salt` (a string) and `sample` (an integer `k`) are present, `<samples>` holds one entry per row, with one sample per column. The sample is null for grouping, `min` and `max` columns. Otherwise it lists the entries of the `k` lowest-ranked items behind the aggregate, lowest first:

| Aggregate  | Item                                       | Rank            | Entry                                                    |
| ---------- | ------------------------------------------ | --------------- | -------------------------------------------------------- |
| `count`    | An event whose value is not null           | `u(id)`         | `id`                                                     |
| `sum`      | An event whose value is a positive integer | `u(id) / value` | `[id, value]`                                            |
| `distinct` | A distinct value                           | `u(value)`      | `[value, id]`, with the id of any event that produced it |

`u(key)` is `(n + 1) / 2^64`, where `n` is the first 8 bytes of `SHA-256(salt ‖ key)` read as a big-endian integer. The salt is UTF-8. The key is the id's 32 bytes, or the value's canonical JSON as UTF-8. With the salt `salt`, `u` of 32 `0xab` bytes is `0.864115113405674`, and `u` of `{"a":"é","b":21000,"c":[1.5,null]}` is `0.6439422860682208`.

Clients SHOULD use a fresh random salt for each request, and the same salt for every relay they merge. A sample with fewer than `k` entries holds every item.

## Merging

Rows from different relays merge when their groups are equal. `min` and `max` merge exactly. For `count`, `sum` and `distinct`, the largest relay value is a lower bound and the sum of the relay values is an upper bound.

With samples, the client sorts the union of the relays' entries by rank. This list contains the `k` lowest-ranked items held by any relay, and each of them appears in the sample of every relay that holds it. If every sample has fewer than `k` entries, the union is exact. Otherwise, the client estimates from the `k` lowest-ranked items, and clamps the estimate to the bounds:

- For `count` and `distinct`, an item held by `m` relays counts `1 / m`. The estimate is the sum over relays of the relay's value times the mean of `1 / m` over its items among the `k`.
- For `sum`, the estimate is the sum of `max(value, 1 / r)` over the `k − 1` lowest-ranked items, where `r` is the `k`-th rank.

If `limit` truncated a relay's rows, merged values are lower bounds.

## Verification

A client checks a sample entry by fetching its event from the same relay with `REQ`, verifying its signature, and evaluating the request over it. A relay's `count` or `distinct` should be close to `(k − 1) / r`, where `r` is the `k`-th rank of its own sample. A relay that inflates a value needs low-ranked entries for items it does not have, and those fail when fetched.

A client audits an aggregate by sending the request again with two more columns, ``bucket(created_at, `<size>`)`` and `{"count": "id"}`, and `until` no later than when the result arrived. The rows that share the audited row's groups must add up to at least its `count` or `sum`, or reach its `min` or `max`. The client then picks one bucket at random, weighted by value, narrows every filter to it, and repeats with a smaller size. Once the bucket's whole window, counted without `where`, fits within the relay's `max_limit`, the client fetches it with `REQ` and evaluates the request locally. If a fraction `f` of a `count` or `sum` is not backed by events, one audit catches it with probability at least `f`. Requests with a filter `limit` or `latest` cannot be audited this way.

Neither check detects events that a relay omits from both `SELECT` and `REQ`.

## Relay information

A relay that supports `SELECT` lists this NIP in `supported_nips`, and its [NIP-11](11.md) document includes limits on the events a request selects, the rows before `limit`, the rows returned, and `k`:

```json
"select": {"max_events": 20000, "max_groups": 100000, "max_rows": 10000, "max_sample": 1024}
```

## Examples

### Reactions by emoji

```json
["SELECT", "a", [{"kinds": [7], "#e": [<id>]}], ["content", {"count": "id"}], {"order": [1, "desc"]}]
["SELECT", "a", [["+", 812], ["🤙", 97], ["-", 3]]]
```

### Replies and comments, and their authors

```json
["SELECT", "b", [{"kinds": [1], "#e": [<id>]}, {"kinds": [1111], "#E": [<id>]}], [{"count": "id"}, {"distinct": "pubkey"}], {"where": "kind == `1111` || contains(tags[?[0]=='e' && [3]=='root'][1], '<id>')"}]
["SELECT", "b", [[42, 17]]]
```

### Accounts followed by the most follows

```json
["SELECT", "c", [{"kinds": [3], "authors": [<pubkey>, ...]}], ["tags[?[0]=='p'][1]", {"distinct": "pubkey"}], {"order": [1, "desc"], "limit": 50}]
["SELECT", "c", [[<pubkey>, 120], [<pubkey>, 97], ...]]
```

### Poll results

```json
["SELECT", "d", [{"kinds": [1018], "#e": [<id>], "until": <poll end>}], ["tags[?[0]=='response'][1]", {"count": "id"}], {"latest": "pubkey"}]
["SELECT", "d", [[<option id>, 88], [<option id>, 41]]]
```

### Zap total, count and senders

```json
["SELECT", "e", [{"kinds": [9735], "#e": [<id>], "authors": [<nostrPubkey>]}], [{"sum": "bolt11(tags[?[0]=='bolt11'][1] | [0]).msats"}, {"count": "id"}, {"distinct": "from_json(tags[?[0]=='description'][1] | [0]).pubkey"}]]
["SELECT", "e", [[5000000, 2, 2]]]
```

### Samples

```json
["SELECT", "f", [{"kinds": [7], "#e": [<id>]}], ["content", {"count": "id"}], {"salt": <random string>, "sample": 256}]
["SELECT", "f", [["+", 812], ["🤙", 97]], [[null, [<id>, ...]], [null, [<id>, ...]]]]
```
