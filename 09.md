NIP-09
======

Event Deletion Request
----------------------

`draft` `optional` `relay`

A special event with kind `5`, meaning "deletion request" is defined as having a list of one or more `e` or `a` tags, each referencing an event the author is requesting to be deleted. Deletion requests SHOULD include a `k` tag for the kind of each event being requested for deletion.

The event's `content` field MAY contain a text note describing the reason for the deletion request.

For example:

```yaml
{
  "kind": 5,
  "pubkey": <32-bytes hex-encoded public key of the event creator>,
  "tags": [
    ["e", "dcd59..464a2"],
    ["e", "968c5..ad7a4"],
    ["a", "<kind>:<pubkey>:<d-identifier>"],
    ["k", "1"],
    ["k", "30023"]
  ],
  "content": "these posts were published by accident",
  // other fields...
}
```

Relays SHOULD delete or stop publishing any referenced events that have an identical `pubkey` as the deletion request. Clients SHOULD hide or otherwise indicate a deletion request status for referenced events. Implementations supporting [NIP-D9](D9.md) MUST exempt marked events as described in "Deletion Request Protection" below.

Relays SHOULD continue to publish/share the deletion request events indefinitely, as clients may already have the event that's intended to be deleted. Additionally, clients SHOULD broadcast deletion request events to other relays which don't have it.

When an `a` tag is used, relays SHOULD delete all versions of the replaceable event up to the `created_at` timestamp of the deletion request event.

## Client Usage

Subject to the NIP-D9 exception below, clients MAY choose to fully hide events referenced by valid deletion request events, show them with an indication that the author has "disowned" them, or replace their content with the deletion reason. These options apply to text notes, direct messages, and other event kinds. If the deletion reason replaces content, the interface should clearly identify it as a deletion reason rather than the original content.

Clients supporting [NIP-D9](D9.md) MUST NOT apply any of those hiding, disowning, or content-substitution behaviors to a marked target as an effect of a deletion request made under the target's own `pubkey`. The independently authorized recipient and delegator operations described in NIP-D9 remain effective.

A client MUST validate that each event `pubkey` referenced in the `e` tag is identical to the deletion request `pubkey` before hiding or deleting that event under this NIP's same-signing-key authority. Independently defined recipient or delegator operations require validation under their owning NIP. Relays can not, in general, perform this validation and should not be treated as authoritative.

Clients display the deletion request event itself in any way they choose, e.g., not at all, or with a prominent notice.

Clients MAY choose to inform the user that their request for deletion does not guarantee deletion because it is impossible to delete events from all relays and clients.

## Relay Usage

Relays MAY validate that a deletion request event only references events that have the same `pubkey` as the deletion request itself, however this is not required since relays may not have knowledge of all referenced events.

## Deletion Request Protection

Relays and clients supporting [NIP-D9](D9.md) MUST NOT delete, suppress, reject republication of, or treat as author-deleted a marked target as an effect of a deletion request made under the target's own `pubkey`. The request MAY be retained or displayed separately without applying those effects to the target.

Protection is evaluated on each target and the authority under which deletion is requested. All non-exempt targets follow their ordinary rules, including unmarked replaceable and addressable events covered by `a` tags. A marker on the request itself does not protect its targets.

The marker does not remove the recipient-based gift-wrap deletion authority in [NIP-59](59.md), including its `p`-tag sweep triggered by kind `5` requests that do not reference the wrap's ID. Nor does it remove a distinct delegator key's existing deletion authority under [NIP-26](26.md).

The same-signing-key exception applies regardless of arrival order. Such a deletion record for an unknown event MUST NOT override a valid marked event received later. Implementations MUST establish the incoming event's validity and protection status before applying that record to reject or suppress it. The complete tag, kind, expiration, republication, and support requirements are defined in NIP-D9.

## Deletion Request of a Deletion Request

Publishing a deletion request event against a deletion request has no effect.  Clients and relays are not obliged to support "unrequest deletion" functionality.
