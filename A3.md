NIP-A3
======

payto: Payment Targets
----------------------

`draft` `optional`

This NIP standardizes how payment addresses are declared across any network or platform.

## Tag Format

Payment targets are specified using `payto` tags with the following structure:

```text
["payto", "<type>", "<address>"]
```

Where:
- The first element is always the literal string `"payto"`
- The second element is the payment `type` (e.g., `"bitcoin"`, `"lightning"`), always lowercase.
- The third element is the `address` (e.g., address, username)

Clients may perform additional network- or platform-specific validation for recognized types.

## Example

```json
{
  "pubkey": "afc93622eb4d79c0fb75e56e0c14553f7214b0a466abeba14cb38968c6755e6a",
  "kind": 10133,
  "content": "",
  "tags": [
    ["payto", "bitcoin", "bc1qxq66e0t8d7ugdecwnmv58e90tpry23nc84pg9k"],
    ["payto", "nano", "nano_1dctqbmqxfppo9pswbm6kg9d4s4mbraqn8i4m7ob9gnzz91aurmuho48jx3c"],
    ["payto", "unknowntype", "l7tbta5b9xze6ckkfc99uohzxd009b0r"]
  ],
  ...
}
```

For each `payto` tag in kind `10133` events, clients can render the payment address as a button or link. Clients may use a specific URI scheme when one is available, such as `bitcoin:<address>` or `ethereum:<address>`. Otherwise fall back to the `payto` URI scheme defined by [RFC-8905](https://www.rfc-editor.org/rfc/rfc8905.html): `payto://<type>/<address>`.

Possible rendered URIs:
- `bitcoin:bc1qxq66e0t8d7ugdecwnmv58e90tpry23nc84pg9k`
- `payto://nano/nano_1dctqbmqxfppo9pswbm6kg9d4s4mbraqn8i4m7ob9gnzz91aurmuho48jx3c`
- `payto://unknowntype/l7tbta5b9xze6ckkfc99uohzxd009b0r`

## Commonly Used Tags

- `bip321` (BIP-321 payment URI, see below)
- `bip352` (silent payments)
- `bip353` (DNS addresses)
- `bitcoin`
- `bitcoincash`
- `cashme` (Cash App `$`-prefixed cashtag)
- `ethereum`
- `lightning` (lightning address)
- `litecoin`
- `monero`
- `nano`
- `paypal`
- `revolut`
- `solana`
- `tron`
- `venmo`
- `zcash`

New widely deployed formats can be added to this list later.

For an unknown payment `type`, in case of ambiguities, a specific address URI scheme may be used when one is available (such as `bitcoincash` from `bitcoincash:<address>`).

## BIP-321 payment URIs

A `bip321` entry holds a complete [BIP-321](https://github.com/bitcoin/bips/blob/master/bip-0321.mediawiki) URI. One URI can offer several ways to pay the same person, and the payer's wallet picks the one it supports:

```json
["payto", "bip321", "bitcoin:?ark=ark1pwh9vsmezqqpjy9akejayl2vvcse6he97rn40g84xrlvrlnhayuuyefrp9nse2yspqqjl5wpy&lno=lno1qgsqvgnwgcg35z6ee2h3yczraddm72xrfua9uve2rlrm9deu7xyfzrc2q3skgumxzcssyeyreggqmet8r4k6krvd3knppsx6c8v5g7tj8hcuq8w6ddl7xu"]
```

- The value is the whole URI, including the `bitcoin:` scheme. Clients use it as it is and do not add another scheme in front.
- It MUST contain only static, reusable payment instructions, such as an on-chain address, `sp=` (silent payments), `lno=` (BOLT12 offer) or `ark=` (Ark address). It MUST NOT contain a `lightning=` BOLT11 invoice or an `amount`, because the entry is published once and paid many times, by different people, for different amounts.
- The payer chooses the amount. A client connected to a wallet with Nostr Wallet Connect can pass the URI and the amount to the wallet's [NWC-321](https://github.com/nostr-wallet-connect/nwc/blob/main/321.md) `pay` method and let the wallet pick the instruction.
- A `bip353` name resolves to the same kind of URI, so a user can publish both. A `lightning` entry (Lightning address) remains a useful fallback for wallets that do not read BIP-321.
