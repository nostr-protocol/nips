# NIP-A3

## payto: Payment Targets

`draft` `optional`

This NIP standardizes how payment addresses are declared across any network or platform.

#### Tag Format

Payment targets are specified using `payto` tags with the following structure:

```text
["payto", "<type>", "<address>"]
["payto", "<type>", "<address>", "<proof>"]
```

Where:
- The first element is always the literal string `"payto"`
- The second element is the payment `type` (e.g., `"bitcoin"`, `"lightning"`), always lowercase.
- The third element is the `address` (e.g., address, username)
- The fourth element is an optional `proof` of ownership of the address, described below.

Clients may perform additional network- or platform-specific validation for recognized types.

### Example

```json
{
  "pubkey": "afc93622eb4d79c0fb75e56e0c14553f7214b0a466abeba14cb38968c6755e6a",
  "kind": 10133,
  "content": "",
  "tags": [
    ["payto", "bitcoin", "bc1qxq66e0t8d7ugdecwnmv58e90tpry23nc84pg9k"],
    ["payto", "nano", "nano_1dctqbmqxfppo9pswbm6kg9d4s4mbraqn8i4m7ob9gnzz91aurmuho48jx3c"],
    ["payto", "unknowntype", "l7tbta5b9xze6ckkfc99uohzxd009b0r"]
  ],
  ...
}
```

For each `payto` tag in kind `10133` events, clients can render the payment address as a button or link. Clients may use a specific URI scheme when one is available, such as `bitcoin:<address>` or `ethereum:<address>`. Otherwise fall back to the `payto` URI scheme defined by [RFC-8905](https://www.rfc-editor.org/rfc/rfc8905.html): `payto://<type>/<address>`.

Possible rendered URIs:
- `bitcoin:bc1qxq66e0t8d7ugdecwnmv58e90tpry23nc84pg9k`
- `payto://nano/nano_1dctqbmqxfppo9pswbm6kg9d4s4mbraqn8i4m7ob9gnzz91aurmuho48jx3c`
- `payto://unknowntype/l7tbta5b9xze6ckkfc99uohzxd009b0r`

### Proof of Ownership

Anyone can publish any address. A `payto` tag may carry a fourth element proving that whoever
published the tag also controls the address, by signing a fixed message with the address's own
private key.

The message is constructed as follows, as a single line with no trailing newline:

```text
nostr-payto <pubkey> <type> <address>
```

Where `<pubkey>` is the lowercase hex public key of the event author, and `<type>` and `<address>`
are byte-for-byte the second and third elements of the tag. Elements are separated by a single
space (`0x20`).

Including the author's pubkey binds the proof to one Nostr identity, so it cannot be lifted out of
someone else's profile. Including the address binds it to one address, for payment types where a
single key controls more than one.

```json
["payto", "bitcoin", "bc1qxq66e0t8d7ugdecwnmv58e90tpry23nc84pg9k", "H1bZ...Kk8="]
```

Signing the above tag, published by pubkey `afc9...5e6a`, means signing exactly:

```text
nostr-payto afc93622eb4d79c0fb75e56e0c14553f7214b0a466abeba14cb38968c6755e6a bitcoin bc1qxq66e0t8d7ugdecwnmv58e90tpry23nc84pg9k
```

#### Signing scheme

The message-signing scheme and the encoding of the `proof` string are whatever the payment type
already uses, not something this NIP defines. For example:

| Type       | Scheme                                     | Encoding      |
| ---------- | ------------------------------------------ | ------------- |
| `bitcoin`  | BIP-322, falling back to legacy BIP-137    | base64        |
| `ethereum` | EIP-191 (`personal_sign`)                  | `0x`-prefixed hex |
| `monero`   | wallet `sign`                              | `SigV2...`    |
| `solana`   | ed25519 over the message bytes             | base58        |

Payment types with no message-signing facility — `paypal`, `venmo`, `cashme`, `revolut`,
`bip353`, `lightning`, and others — have no proof, and the fourth element is omitted.

#### Client behavior

Proofs are advisory. Verifying one requires the signature and address machinery of the payment
network in question, which most clients will not have for most types.

- Clients MAY ignore the `proof` element entirely. Doing so is not a security regression: a tag
  without a proof is exactly as trustworthy as it was before this section existed.
- A missing proof MUST NOT be presented as a warning or as evidence that an address is
  illegitimate. Most addresses cannot be proven.
- A proof that is present and fails to verify SHOULD be treated as if the whole tag were absent,
  since it is either malformed or an address the author does not control.
- Clients that surface a verified proof to the user should be precise about what it says. It says
  that the holder of the address's private key consented to it appearing in this profile. It does
  not say that the address is safe, that the payment will reach the person the user has in mind,
  or that the key is still held by the same party today — a proof has no expiry and remains valid
  for as long as the address does.

### Commonly Used Tags

- `bip352` (silent payments)
- `bip353` (DNS addresses)
- `bitcoin`
- `bitcoincash`
- `cashme` (Cash App `$`-prefixed cashtag)
- `ethereum`
- `lightning` (lightning address)
- `litecoin`
- `monero`
- `nano`
- `paypal`
- `revolut`
- `solana`
- `tron`
- `venmo`
- `zcash`

New widely deployed formats can be added to this list later.

For an unknown payment `type`, in case of ambiguities, a specific address URI scheme may be used when one is available (such as `bitcoincash` from `bitcoincash:<address>`).
