NIP-0D
======

Relay Onion Addresses
---------------------

`draft` `optional` `relay`

A relay that is also a Tor onion service can advertise its onion address, so clients can stay within the Tor network instead of leaving it through an exit. The address is provided via the `Onion-Location` HTTP header[^onion-location] and a DNS record. It is normally an `http` URL, but relays with a TLS certificate for their onion address can use `https`.

## `Onion-Location` header

```
Onion-Location: http://abc.onion/
```

To connect to the relay, clients replace `http` with `ws` and `https` with `wss`.

## DNS `TXT` record

There is no agreed standard for publishing an onion address in DNS: the Tor Project lists DNS-based discovery as research[^dns]. This NIP therefore uses a simple `TXT` record at `_onion.<relay host>` holding the same value as the header:

```
_onion.relay.example.com. 86400 IN TXT "http://abc.onion/"
```

Here too, clients replace `http(s)` with `ws(s)` to connect.

## Relays

A relay with an onion address MUST send the `Onion-Location` header on HTTP responses from its clearnet address, including the [NIP-11](11.md) document and the WebSocket upgrade response. The value SHOULD use the `http` scheme, since Tor already encrypts the connection. A relay with a TLS certificate for its onion address MAY use `https`.

A relay SHOULD also publish the `TXT` record. The record SHOULD have a TTL of 24 hours (86400 seconds), so that clients look it up rarely.

A relay that supports [NIP-42](42.md) MUST accept `AUTH` events whose `relay` tag names either its clearnet or its onion address.

Relays implementing this NIP SHOULD include `"0D"` in the `supported_nips` field of their [NIP-11](11.md) document.

## Clients

Clients MUST ignore an advertised value unless its host ends in `.onion`, since connecting to it might use `ws` without TLS. To connect, they use the host and port of the advertised value with the path of the relay URL, so `wss://relay.example.com/nostr` with `http://abc.onion/` becomes `ws://abc.onion/nostr`.

Clients MUST only accept the header from a response received over TLS.

Clients SHOULD first try to learn the onion address from the header. When the relay cannot be reached to read it, for example because it refuses Tor exits, a client SHOULD look up the `TXT` record. Tor's own resolver cannot look up `TXT` records, so clients SHOULD use DNS-over-HTTPS through Tor, and MAY fall back to a lookup outside Tor, which tells the resolver which relay they are interested in. Clients SHOULD save the result, to avoid looking it up again. The record is only as trustworthy as its DNS answer: clients SHOULD require a DNSSEC-validated answer or use a resolver they trust.

When both the header and the record are available and differ, clients SHOULD use the header.

A client that learns an onion address SHOULD, while routing that relay through Tor, connect to the onion address instead of the clearnet one. If the onion address cannot be reached, clients MAY fall back to the clearnet address.

Clients SHOULD treat a relay URL and the onion URL it advertises as the same relay, for instance when both appear in a [NIP-65](65.md) list.

[^onion-location]: Specified in Tor Browser's [proposal 100](https://gitlab.torproject.org/tpo/applications/tor-browser-spec/-/blob/main/proposals/100-onion-location-header.txt) and documented by the Tor Project at [Onion-Location](https://community.torproject.org/onion-services/advanced/onion-location/). The value must be an `http` or `https` URL, and Tor Browser only accepts it from a site served over HTTPS that is not itself an onion service.

[^dns]: See the Tor Project's [Onion Association](https://onionservices.torproject.org/research/proposals/usability/discovery/onion-association/) overview and its draft [Specs for .onion in the DNS](https://onionservices.torproject.org/research/appendixes/dns/), which consider `TXT`, `SRV`, `HTTPS`/`SVCB` and a new record type, as well as Tor Browser [issue 41325](https://gitlab.torproject.org/tpo/applications/tor-browser/-/work_items/41325) on `HTTPS` records and an earlier [tor-dev thread](https://www.mail-archive.com/tor-dev@lists.torproject.org/msg09563.html) on DNSSEC-signed `TXT` records.
