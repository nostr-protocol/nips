NIP-D9
======

Deletion Request Protection
---------------------------

`draft` `optional` `relay` `client`

> D9 is the proposed NIP number, pending acceptance.

This NIP defines an event tag that exempts an event from same-signing-key deletion requests under [NIP-09](09.md) and author-based purges under [NIP-62](62.md). It does not remove independently defined recipient or delegator deletion authority. An expiration timestamp signed into the event remains effective under [NIP-40](40.md).

This is useful when an event must remain available despite later requests from its signing key, including applications that use shared signing keys or retain protocol history. It does not require a relay to accept an event or store it indefinitely.

## The tag

An event opts in by including exactly one tag with the following contents:

```json
["no_delete"]
```

The tag name is case-sensitive. The tag MUST contain exactly one element. A relay supporting this NIP MUST reject publication of an event containing more than one `no_delete` tag, or a `no_delete` tag with additional elements, as malformed, using the NIP-01 `invalid:` response prefix.

A **marked event** is an otherwise valid NIP-01 event that satisfies this NIP's tag, kind, and expiration requirements. Its NIP-01 event ID and signature MUST be verified before it is treated as marked.

Supporting clients MUST treat a malformed marker, a marker on an ineligible kind, or a marker combined with malformed expiration metadata as providing no protection. Such metadata MUST NOT by itself invalidate an otherwise valid Nostr event for the client; the event remains subject to its ordinary kind and application rules. An application that explicitly requires protection may refuse an event that does not provide it.

The marker is part of the signed event. Adding, removing, or changing it creates a different event with a different event ID. Protection cannot be added to or withdrawn from an existing event by a separate request or author metadata update.

### Eligible event kinds

This version applies only to event kinds outside the replaceable, addressable, and ephemeral classes defined by [NIP-01](01.md). In particular, kinds `0` and `3`, and kinds in the range `10000` through `39999`, are ineligible.

Supporting relays MUST reject publication of an event carrying `no_delete` on an ineligible kind, using the `restricted:` response prefix. This is a restriction on this extension, not evidence that the event is invalid under NIP-01. Receiving clients handle the event as unmarked if it is otherwise valid under their ordinary rules.

This restriction avoids conflicts with replacement and ephemeral storage rules. An eligible kind is still subject to the relay's normal admission and storage policy.

## Deletion requests

For a marked event, supporting relays and clients MUST NOT do any of the following as an effect of a NIP-09 request made under the event's own `pubkey`, or of a NIP-62 author-based purge under that key. The independently authorized recipient and delegator operations below remain effective.

- delete or discard the event;
- suppress it from otherwise matching subscriptions, queries, synchronization, or application presentation;
- reject its subsequent publication or import;
- treat it as author-deleted, including substituting a deletion reason for its content.

An implementation MAY retain or display the request separately without applying these effects to the marked event. Acceptance of a request does not imply that every named target was deleted.

Protection is evaluated on each target event and the authority under which deletion is requested. All non-exempt targets follow their ordinary deletion rules, including unmarked replaceable and addressable events. A marker on a deletion request does not protect its targets, and an unmarked request does not remove a target's protection.

Kinds `5` and `62` are eligible kinds. A valid marker on such a request protects that request event's own record against same-signing-key deletion; it does not change the request's authority, effect on other targets, or existing rules against undoing deletion requests.

### NIP-09

A NIP-09 request signed by the same `pubkey` as a marked target does not authorize deletion of that target. An implementation MUST NOT record an effective same-signing-key deletion outcome for a marked target because it receives such a request.

### NIP-62

Marked targets are exempt from NIP-62 author-based purges, including requests addressed to a particular relay and requests addressed to `ALL_RELAYS`. The request's `pubkey` must match the target's `pubkey` for this author-based exemption to apply. Recipient-based gift-wrap purges are not exempted.

The exception also applies to NIP-62's requirement to prevent republication of events removed by an author-based purge. A request, deletion record, or author cutoff MUST NOT cause an otherwise acceptable marked event to be rejected or suppressed under that author-based authority. This includes marked events whose `created_at` falls within the request's author-purge range.

An implementation MUST NOT disable an author's publication of marked events solely as an indirect consequence of a request to vanish. Independently applicable admission and abuse policies remain effective.

### Recipient and delegator authority

The recipient-based gift-wrap deletion rules in [NIP-59](59.md) and NIP-62 remain unchanged, even when a gift wrap is marked. In particular, NIP-59's `p`-tag sweep may be triggered by either a kind `5` or kind `62` signed by the recipient, without an `e` tag naming the wrap. The marker does not exempt a wrap from that recipient-based operation, including when the recipient also controls its signing key. This NIP introduces no recipient cutoff or new timestamp condition for such purges.

Where a distinct delegator key has deletion authority under [NIP-26](26.md), this NIP does not remove that authority. A delegatee's marker waives deletion through the event's own signing key; it cannot waive authority held by the delegator.

## Arrival order and republication

Protection against same-signing-key requests MUST have the same effect regardless of whether an implementation receives the marked event or the deletion request first. Supporting implementations MUST establish an incoming event's validity and protection status before applying a same-signing-key deletion record that would reject or suppress that event.

A same-signing-key deletion record for an unknown event does not establish that the event is unmarked. Implementations MAY retain that record and apply it if an unmarked target later arrives, but MUST exempt a valid marked target from that same-signing-key operation.

The same rules apply to stored copies, backfill, synchronization, imports, and republication of byte-identical events. A same-signing-key deletion record retained before support for this NIP was enabled MUST NOT override a marked event received after support is enabled. Protection cannot recover a copy that has already been lost, but another available copy remains eligible for republication under these same-signing-key rules; other deletion authority remains effective.

This NIP imposes no additional publisher authentication requirement. Any client may republish a marked event subject to the relay's normal policies and any independently applicable NIPs. In particular, a [NIP-70](70.md) `-` tag, if present, retains its own publication restrictions; `no_delete` neither implies nor disables that tag.

## Expiration

A marked event MAY also contain a NIP-40 `expiration` tag:

```json
[
  ["no_delete"],
  ["expiration", "1800000000"]
]
```

An event containing a `no_delete` tag MUST contain at most one `expiration` tag, and that tag MUST contain exactly one value. That value MUST be an ASCII decimal representation of an integer from `0` through `18446744073709551615`, with no sign, whitespace, or leading zeroes except for the value `0`. Supporting relays MUST reject publication of an event containing `no_delete` and malformed or repeated expiration tags, using the `invalid:` response prefix. Receiving clients treat such an event as unmarked if otherwise valid under their ordinary rules.

Implementations MUST interpret the timestamp without overflow or loss of integer precision. A relay unable to represent an otherwise valid timestamp MAY reject its publication under local policy using `restricted:`, but MUST NOT truncate, wrap, or reinterpret that value as an earlier expiration.

The marker MUST NOT override NIP-40. Expired marked events remain subject to its rules for expiration, delivery, and publication. A supporting relay that does not implement NIP-40 MUST reject marked events carrying `expiration`, using `restricted:`; it MUST NOT accept the combination while ignoring expiration.

Expiration does not revoke the marker. An expired marked copy that remains stored is still exempt from same-signing-key deletion requests. This proposal preserves NIP-40's allowance to retain expired data and does not provide request-based physical erasure after expiry. An author who needs that ability should not choose this marker.

The expiration timestamp is fixed by the signed event. A later deletion request cannot advance it, and a later event cannot replace it on the original event ID. An event with identical content but a different expiration is a separate event; an implementation MUST NOT transfer the new event's expiration or deletion status to the original solely because their content matches.

Absence of an expiration tag introduces no protocol expiration deadline and makes no promise of permanent storage. The expiration syntax restriction above applies only to marked events; this NIP does not change the handling of unmarked events under NIP-40.

## Relay and client behavior

Relays implementing this NIP MUST advertise its assigned integer NIP number in [NIP-11](11.md)'s `supported_nips`. Implementing the complete deletion, republication, ordering, kind, and tag requirements is necessary to advertise support.

Clients relying on deletion protection MUST establish relay support before counting a publication there as protected. A successful NIP-01 `OK` response, or acceptance of an otherwise unknown tag, is not evidence of support. This NIP defines no new client-relay message type.

Clients relying on both protection and expiration MUST establish support for both this NIP and NIP-40. Advertising this NIP alone does not advertise NIP-40 support.

A client MUST NOT silently remove the marker to retry a failed protected publication. It MAY publish to relays without support as an additional delivery path, but MUST NOT treat those copies as protected.

Rejections required by this extension are scoped to the rejecting relay. Clients MUST NOT infer from such a response alone that the event is invalid under NIP-01 or unusable on other relays. For an ineligible kind, an application MAY instead create a separate unmarked event under its ordinary unprotected publication workflow, but MUST NOT represent that publication as fulfilling a protection requirement.

Supporting clients MUST apply the target-event exceptions even if a deletion request is received from a relay that does not implement this NIP. They MAY additionally retain copies independently of relay storage.

## Storage policy and limitations

Protection exempts an event from the same-signing-key protocol requests described above; it does not require unlimited storage or acceptance. Independently applicable moderation, capacity, retention, admission, and local user policies remain effective. The existence of a valid protocol deletion request alone MUST NOT be treated as an independent policy reason to bypass protection.

This NIP does not constrain removal required by independently applicable operator obligations, including legal obligations, even if first communicated in a deletion request. It does not determine those obligations. Likewise, an operator may act on independently established abuse or key compromise reported in a request; the request's signature alone is not an automatic override of protection.

The marker grants no additional deletion authority. An author cannot use it to change another event, and the marker does not identify who controls a shared signing key.

The holder of an event's signing key choosing the marker relinquishes same-signing-key deletion by protocol request for that event on supporting implementations. Recipient and delegator authority is not relinquished. Anyone can retain or republish an available copy subject to applicable publication policies, other deletion authority, and expiration. Users who need same-signing-key request-based deletion, including of retained expired copies, SHOULD NOT use this marker for those events.

This NIP provides no assurance that an unsupported or malicious relay will preserve an event, or that an expired event has been physically erased. Applications requiring availability still need independent delivery paths or retained copies.

## Examples of required behavior

These cases assume valid signatures, ordinary admission acceptance, no independently applicable storage-policy removal, and no recipient or delegator deletion authority unless that is the case being tested. Publication rejection rows describe relay behavior; receiving clients handle malformed or ineligible markers as providing no protection. Expiration behavior cases additionally assume NIP-40 support.

| Input or sequence | Required behavior |
| --- | --- |
| Marked event, then a valid same-author kind `5` request | Do not delete, suppress, or treat the target as author-deleted |
| Same-signing-key kind `5` request for an unknown ID, then a marked event with that ID | Do not apply the same-signing-key deletion record to the marked target |
| Marked event, then a kind `62` request under its signing key | Exempt the event from the author-based purge and corresponding republication ban |
| Kind `62` request, then a marked event within its author cutoff | Do not reject the event under that author-based purge authority |
| Marked gift wrap addressed to the requesting recipient key, then kind `5` or `62` | Apply the ordinary NIP-59/NIP-62 recipient purge; the marker does not waive recipient authority |
| A marked delegated event, then a deletion request exercising a distinct NIP-26 delegator key's authority | Apply the ordinary delegator rule; the marker does not waive that authority |
| One same-signing-key request covering a marked event and an unmarked replaceable or addressable event | Exempt the marked event; process the unmarked target normally, including `a`-tag deletion |
| Marked event with a future expiration, then a deletion request | Do not advance or otherwise change its expiration |
| Marked event reaches its signed expiration | Apply NIP-40 normally |
| An expired marked copy remains stored, then a same-signing-key deletion request arrives | The copy remains exempt; expiration does not revoke the marker |
| A relay without NIP-40 receives a marked event carrying `expiration` | Reject with `restricted:` |
| Two different event IDs with identical content and different expiration tags | Evaluate each event's protection and expiration independently |
| Two `no_delete` tags, or `["no_delete", "1"]` | Relay rejects with `invalid:`; a receiving client treats the event as unmarked if otherwise valid |
| A `no_delete` tag on kind `0`, `10002`, `20000`, or `30023` | Relay rejects with `restricted:`; a receiving client treats the event as unmarked if otherwise valid |
| An event with `no_delete` and repeated expiration tags, `"-1"`, `"01"`, or `"18446744073709551616"` as its expiration | Relay rejects with `invalid:`; a receiving client treats the event as unmarked if otherwise valid |
| A valid expiration above a relay's representable timestamp range | Reject with `restricted:` if needed; never overflow or shorten the expiration |

## Compatibility

No new event kind, signature scheme, or connection authentication is introduced. Unmarked events retain their existing behavior. Implementations without this NIP may accept marked events while applying ordinary deletion rules, which is why support discovery is required when protection is relied upon.

Adoption requires the accompanying NIP-09 and NIP-62 exceptions. In particular, NIP-62's author-based full-purge and republication requirements are qualified for marked events. Recipient and delegator deletion behavior remains unchanged.
