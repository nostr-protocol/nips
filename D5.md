NIP-D5
======

DNSSEC Proofs
-------------

`draft` `optional`

This NIP defines `kind:9364`, an event that carries DNSSEC-signed DNS records. With it, a DNS answer can be checked by anyone, without asking a resolver. Additionally, a record that no longer exists can still be verified.

## Motivation

Some things on Nostr depend on what a DNS record says: the payment instructions of a [BIP 353](https://github.com/bitcoin/bips/blob/master/bip-0353.mediawiki) address, the key or service a domain delegates to. A client that reads such a record has to validate DNSSEC itself or trust a resolver, and either way it cannot show anyone else what it saw. An event that says "I paid the offer that `user@example.com` named" is a bare claim.

A DNSSEC-signed answer does not need a resolver to be believed. The record, the signature over it, and the keys and delegations up to the root can be checked offline against the root trust anchor. [RFC 9102](https://www.rfc-editor.org/rfc/rfc9102) defines a serialization for such a chain. BIP 353 uses it to hand proofs to hardware signers and [bLIP 32](https://github.com/lightning/blips/blob/master/blip-0032.md) carries it over onion messages. This NIP puts it in events, so that:

- an event that relies on a DNS record can reference the proof, and a reader can check the claim later;
- the parts of a proof that many names share, such as the keys of the root and of `nl`, are published once and reused;
- a client that cannot reach a resolver can still obtain the records.

## Event

`kind:9364` is a regular event. The number is that of [RFC 9364](https://www.rfc-editor.org/rfc/rfc9364), "DNS Security Extensions (DNSSEC)", the document that describes DNSSEC as a whole.

```jsonc
{
  "kind": 9364,
  "content": "<base64 of resource records>",
  "tags": [
    ["i", "dns:example.com?type=DS"],
    ["i", "dns:example.com?type=DNSKEY"]
  ]
}
```

### Content

The `content` is the base64 encoding ([RFC 4648](https://www.rfc-editor.org/rfc/rfc4648) section 4, with padding) of one or more RRsets and their signatures in the format of an RFC 9102 `AuthenticationChain`: resource records in DNS wire format (owner name, type, class, TTL, RDATA length, RDATA), with uncompressed names, one after another.

- Every record MUST be of class `IN`.
- Every RRset MUST be complete and MUST come with at least one `RRSIG` record that covers it, in the same event. An RRset MUST NOT be spread over several events.
- The decoded content MUST NOT be larger than 16384 bytes.
- The order of the records carries no meaning. A publisher SHOULD use the [canonical serialization](#canonical-serialization).

### Tags

The event has one `i` tag for each RRset in its content, and none for the `RRSIG` records. The value is a `dns:` URI ([RFC 4501](https://www.rfc-editor.org/rfc/rfc4501)) of the form `dns:<name>?type=<TYPE>`:

- `<name>` is the absolute owner name in lowercase without the trailing dot, with internationalized labels as A-labels. The root is `.`.
- `<TYPE>` is the mnemonic of the record type in uppercase, or `TYPE<number>` ([RFC 3597](https://www.rfc-editor.org/rfc/rfc3597)) for a type without one.

For example `dns:.?type=DNSKEY`, `dns:nl?type=DS`, `dns:sjors.user._bitcoin-payment.sprovoost.nl?type=TXT`.

This is the `i` tag of [NIP-73](73.md), with DNS as one more kind of external identifier. The tags exist so that relays can index what an event holds. A reader MUST NOT believe them; what an event proves follows from its content alone.

### Author

Anyone can publish any proof. A client SHOULD NOT restrict a search for proofs to particular authors.

## Splitting a Chain

To validate one RRset a reader needs the `DNSKEY` RRset of the root, the `DS` and `DNSKEY` RRsets of every zone on the way down, and the RRset itself. All of these MAY be in one event, which is then the RFC 9102 chain as it is used elsewhere.

A publisher SHOULD instead split the chain into:

- one event for each zone, with the `DS` and `DNSKEY` RRsets of that zone (for the root, the `DNSKEY` RRset only);
- one event for each zone that signed records of the answer, with those records: the RRset asked for and any `CNAME`, `DNAME`, `NSEC` and `NSEC3` RRsets that lead to it. For a record at a plain name this is one event with one RRset.

The zone events are the same for every name below the zone. Measured on 27 November 2026 for the BIP 353 address `sjors@sprovoost.nl`:

| Event                              | Records (bytes) | `content` (characters) |
| ---------------------------------- | --------------- | ---------------------- |
| `.` `DNSKEY`                       | 1111            | 1484                   |
| `nl` `DS` and `DNSKEY`             | 685             | 916                    |
| `sprovoost.nl` `DS` and `DNSKEY`   | 474             | 632                    |
| the `TXT` RRset of the address     | 426             | 568                    |
| Total                              | 2696            | 3596                   |

The id, pubkey, signature, tags and JSON syntax of an event add about 400 to 500 bytes. Four events instead of one therefore cost about 1.4 kB once, and every further address on the same domain needs one new event of about 1 kB instead of 4.1 kB. Two thirds of this chain, about 2.4 kB, is the root and the top-level domain, which a single event with the whole chain would repeat in every proof. Putting each RRset in its own event would add two more events and share nothing more, because the `DS` and `DNSKEY` RRsets of a zone are always needed together.

Before publishing, a client SHOULD look for events that already hold the RRsets it would publish, and reference those instead. An event with the same content can be referenced as it is; the canonical serialization makes two clients that saw the same DNS answer produce the same content. An event that holds the same RRsets with other signatures, because it was made at another moment, can be referenced when the proof still validates with it. Whoever runs a service that many payers or readers use can therefore publish proofs ahead of time, and others reference them without signing anything.

### Canonical Serialization

- RRsets are ordered by the number of labels of the owner name, then by owner name, then by type number.
- Within an RRset, records are in the canonical order of [RFC 4034](https://www.rfc-editor.org/rfc/rfc4034) section 6.3, followed by the `RRSIG` records that cover the RRset, ordered the same way.
- The TTL of every record is the Original TTL of an `RRSIG` that covers it. For an `RRSIG` record it is its own Original TTL.

## Referencing a Proof

An event that relies on a DNS record references the proof events by id:

```json
["dnssec", "<event id>", "<relay URL>"]
```

with one tag for each event a reader needs. That is four in the example above, and seven for a name answered by a wildcard `CNAME` to another domain. The NIP that defines the referencing event says which name and type have to validate, at what time, and what the RRset has to say.

The events themselves cannot be changed, but the records in them can be published again by anyone, in a new event with a new id. A reader that cannot find a referenced event MAY look for the same records by `#i`.

## Finding a Proof

```json
{"kinds": [9364], "#i": ["dns:.?type=DNSKEY", "dns:nl?type=DS", "dns:nl?type=DNSKEY"]}
```

A publisher SHOULD set `created_at` to the time it obtained the records, so that `since` and `until` narrow a search to proofs that can be valid at the time of interest. A reader does not rely on `created_at` for anything else.

## Validation

A reader collects the RRsets of the events it considers: the referenced ones, or the ones a search returned. Two events may hold different versions of the same RRset, for example from before and after a key change. Each version is a candidate of its own. Records from different events MUST NOT be combined into one RRset.

An RRset validates at a time `t` when, following [RFC 4035](https://www.rfc-editor.org/rfc/rfc4035) section 5:

1. a `DNSKEY` RRset of the root has a key that matches a root trust anchor the client is configured with, and is signed by that key;
2. for every zone on the way down, a `DS` RRset of the zone is signed by a validated key of an ancestor zone, and a `DNSKEY` RRset of the zone has a key that matches one of those `DS` records and is signed by that key;
3. the RRset is signed by a validated key of the zone its `RRSIG` names as signer, which is the owner name or an ancestor of it;
4. `t` lies between the inception and the expiration of every `RRSIG` used.

The root trust anchors come from [IANA](https://www.iana.org/dnssec/files), not from an event.

A reader MUST NOT accept signature algorithms or `DS` digests based on MD5 or SHA-1, or RSA keys shorter than 1024 bits. It SHOULD support the algorithms RSASHA256 (8), ECDSAP256SHA256 (13) and ED25519 (15) and the digest SHA-256 (2).

### Wildcards

An answer was expanded from a wildcard when the Labels field of its `RRSIG` is smaller than the number of labels of its owner name. The signature is then checked over the wildcard name, and the answer validates only together with a validated `NSEC` or `NSEC3` record of the same zone showing that neither the name nor a closer wildcard exists ([RFC 4035](https://www.rfc-editor.org/rfc/rfc4035) section 5.3.4, [RFC 5155](https://www.rfc-editor.org/rfc/rfc5155) section 8.8):

- an `NSEC` record covers the name, and the longest name it shares with the owner or the next name of that record is the one the wildcard sits directly below. An `NSEC` record whose owner is above the name and has a `DNAME`, or an `NS` without `SOA`, shows nothing;
- an `NSEC3` record covers the hash of the name one label below the name the wildcard sits directly below. A reader MUST NOT use an `NSEC3` record with the opt-out flag for this, and SHOULD limit the number of hash iterations it accepts.

### CNAME and DNAME

When the name has a `CNAME` RRset instead of the RRset asked for, a reader validates the `CNAME`, which may itself come from a wildcard, and then the RRset at its target. When a name above it has a `DNAME` RRset, the reader validates that and continues at the name the `DNAME` redirects to. The target can be in another zone, whose `DS` and `DNSKEY` RRsets are then needed as well. A reader SHOULD limit how many aliases it follows.

The unsigned `CNAME` that a resolver adds to an answer below a `DNAME` is not part of a proof.

A reader that does not implement wildcards or aliases MUST treat such an answer as not validated.

Proving that a name or type does not exist is out of scope.

## Limits

- A proof shows that a record was published and signed for a period that includes `t`. It does not show that the record is still current. The owner of a zone can replace a record while the signature over the old one remains valid. In the zones measured for this draft signatures were valid for between two days and four weeks.
- A client that is about to act on a record, for example to pay, chooses between two things. Asking DNS gives the current record and tells a resolver what the client is interested in. Asking a relay for a proof keeps the question away from the resolver, and may return a record that has been replaced. A client that takes the record from proofs SHOULD first ask relays that already know what it is doing, such as the relay of the service it is using, before relays to which the question is news. Of the answers that validate it MUST take the one the zone signed last: the one with the latest inception in the `RRSIG` over the RRset at the name asked for, or over the `CNAME` or `DNAME` there. `created_at` does not decide this. A relay operator who publishes proofs on a schedule bounds how old the record can be.
- The `DS` and `DNSKEY` RRsets can come from relays in either case: a stale one that is still within its validity can at worst vouch for a key the zone has since retired, which matters only if that key was compromised.
- The full chain of the example was valid for another twelve days when it was fetched. Proofs do not stay valid; they stay checkable for the time `t` they were referenced for. That is the reason this kind is not replaceable.
- `created_at` is not authenticated. Someone can sign an event today, give it an old date and reference an old proof. A NIP that references proofs has to consider what that allows.
- DNSSEC places trust in the root, the registry of the top-level domain and whoever holds the keys of the zone. A proof is no stronger than that.
- A relay asked for proofs by `#i` learns the name, as a resolver does from a query. One question can cover a whole chain: the RRset, a `CNAME` in its place, and the `DNSKEY` of every name above it, since a zone's event carries both its `DS` and `DNSKEY` tags.
- Relays decide how long they keep events. Proof events SHOULD NOT carry an `expiration` tag.
- Validation costs signature checks. A reader SHOULD limit the number of proof events it accepts for one claim and the number of candidates it tries.

## Why Not

- **A tag on the referencing event that holds the chain.** [NIP-DB](https://github.com/nostr-protocol/nips/pull/2487) proposes this for its own claim. Every event that refers to the same record then carries about 3.6 kB.
- **An addressable kind.** A new version replaces the old one, and with it the proof that an earlier event referenced. Addresses are also per author, and the author does not matter here.
